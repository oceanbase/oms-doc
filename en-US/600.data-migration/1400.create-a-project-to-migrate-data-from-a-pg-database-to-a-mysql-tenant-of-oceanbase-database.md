# Migrate data from a PostgreSQL database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a PostgreSQL database to OceanBase Database Community Edition.

## Background information

In the OMS Community Edition console, you can create a data migration task to migrate data from a PostgreSQL database to OceanBase Database Community Edition. You can seamlessly migrate existing business data and incremental data from the source database to OceanBase Database Community Edition by using schema migration, full migration, and incremental synchronization.

PostgreSQL databases support single-primary, single-standby, and primary-standby modes. When you migrate data from a PostgreSQL database to OceanBase Database Community Edition, the operations supported by different types of data sources vary.

| Type | Supported operations |
|-----|----------------------------------------------------------|
| Single-primary database | Schema migration + full migration + incremental synchronization + full verification + reverse incremental synchronization |
| Single-standby database | Schema migration + full migration + full verification |
| Primary-standby database | Primary database: Incremental synchronization + reverse incremental synchronization <br>Standby database: Schema migration + full migration + full verification |

## Prerequisites

* You have created the corresponding schema in OceanBase Database Community Edition. OMS Community Edition supports migrating tables and columns. Therefore, you need to create the corresponding schema in OceanBase Database Community Edition.

* You have created a database user for data migration tasks in the source PostgreSQL database and OceanBase Database Community Edition, and granted the corresponding permissions to the database user. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

* If you choose **<UI-TERM key="oms-community.Sync.constants.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** > **<UI-TERM key="oms-community.components.SyncOption.CheckSyncKind.SynchronousDdl">DDL Synchronization</UI-TERM>**, you need to create a trigger and a table for recording DDL statements. For more information, see [Create a trigger](../1200.reference-guide/500.create-a-trigger.md).

## Limitations

* **Limitations on operations on the source database**

   **Do not perform DDL operations to change the schema of a database or table during schema migration or full migration. Otherwise, the data migration task may fail.**

* The supported PostgreSQL database versions are V10.x, V11.x, V12.x, V13.x, V14.x, V15.x, V16.x, and V17.x.

* OMS Community Edition supports migrating tables with primary keys, tables without primary keys, and NOT NULL unique key tables from a PostgreSQL database to OceanBase Database Community Edition.

* At present, direct load does not support writing data in the Latin1 character set. An exception will be thrown.

* If a PostgreSQL database has read-only permissions, the data migration task fails. You can set the `default_transaction_read_only` parameter to `off` to disable the read-only permission.

   ```SQL
   ALTER ROLE <user_name> SET default_transaction_read_only TO off;
   ```

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If a trigger exists, the data migration task may fail.

* When you migrate partitioned tables from a PostgreSQL database to OceanBase Database Community Edition, note the following limitations:

  * The table structures of the parent table and child tables must be the same.

  * The primary key columns, NOT NULL unique key columns, and partitioning columns of the parent table and child tables must be the same, or the primary key columns and NOT NULL unique key columns must include the partitioning columns.

  * From the perspective of the parent table, the primary key and NOT NULL unique key must be unique.

* The `REPLICA IDENTITY` parameter of the parent table and child tables in the PostgreSQL database must be set to FULL.

  * If the `REPLICA IDENTITY` parameter is not set to FULL, business data update and delete operations may fail.

  * When you specify a wildcard in the migration object, the PostgreSQL database must subscribe to all tables in the selected database, including the selected tables, unselected tables, and newly added tables. The `REPLICA IDENTITY` parameter of all tables must be set to FULL. Otherwise, business data update and delete operations may fail.

* OMS Community Edition does not support migrating unlogged tables and temporary tables from a PostgreSQL database.

* Data source identifiers and user accounts must be globally unique in the OMS system.

* OMS Community Edition supports migrating only databases, tables, and columns whose names are ASCII characters and do not contain special characters (including line breaks and spaces, and |"'`()=;/&).

* OceanBase Database Community Edition does not support specifying array subscripts, while PostgreSQL supports specifying array subscripts. The format is `[start index: number of array elements]={x,x,x,x}`.

   For example, the array subscript specified in PostgreSQL is `[-1:10]={0,0,0,100,101,102,NULL,NULL,NULL,NULL,NULL,200}`. When the data is written to OceanBase Database Community Edition, the subscript is removed, and the data is written as `{0,0,0,100,101,102,NULL,NULL,NULL,NULL,NULL,200}`. When the data is written back to PostgreSQL, the subscript is reset to 1. If your application depends on the subscript, the following issues may occur.

  * An error is returned when a line break is included in a string array.

  * PostgreSQL supports multidimensional arrays. For example, the VARCHAR(255)[] data type in PostgreSQL can store multidimensional array data:

    * {{a,b},{c,d}}

    * {{{1,a},{2,b}},{{1,c},{2,d}}}

    * ...

    OceanBase Database Community Edition does not support multidimensional arrays. In this case, OMS Community Edition provides the following two solutions. You can choose the one that suits your business.

    * Solution 1: Create an array of the corresponding dimension for the destination field based on the actual data dimension. For example, if the data in the PostgreSQL database is a two-dimensional array, create a two-dimensional array in OceanBase Database Community Edition.

    * Solution 2: Store the data in the destination field in the JSON format.

## Considerations

* We recommend that you migrate data from no more than 1,000 tables at a time to avoid affecting the running of data migration tasks.

* If a table has no primary key or all columns are unique keys with the NOT NULL constraint, duplicate data may be generated during data migration.

* In the reverse incremental scenario, data is migrated by using full-column matching for UPDATE and DELETE operations. This may result in the following issues:

  * Performance issues.

    Since no primary key index exists, each UPDATE or DELETE operation involves a full table scan.

  * Data inconsistency.

    Since the LIMIT clause is not supported for UPDATE and DELETE operations in a PostgreSQL database, when multiple rows are matched during full-column matching, more rows may be updated or deleted in the destination database than in the source database. For example, in a table t1 without a primary key, two rows with c1=1 and c2=2 are stored in the source database. When one of the rows is deleted in the source database, the `where c1 = 1 and c2 = 2` condition causes both rows to be deleted in the destination database. This results in data inconsistency between the source and destination databases.

* In the reverse incremental scenario from a PostgreSQL database to OceanBase Database Community Edition, if OceanBase Database Community Edition is of a version earlier than V3.2.x and the source table is a multi-partition table with a global unique index, updating the partition key values may result in data loss during data migration.

* If you change the unique index in the destination database, you must restart the incremental synchronization component. Otherwise, data inconsistency may occur.

* If the clocks of nodes or between the client and server are out of sync, the delay time (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay time may be negative. If the clock is later than the standard time, the delay time may be positive.

* In the scenario of table aggregation:

  * We recommend that you use an import object or matching rule to map the relationship between the source and destination databases.

  * We recommend that you create the table structure in the destination database. If you use OMS Community Edition, skip failed objects during the schema migration step.

* Inconsistent data may occur if the table structures of the source and destination databases are not exactly the same. The following scenarios are known to cause this issue:

  * When you manually create a table structure that exceeds the supported scope of OMS Community Edition, implicit conversion issues may occur, resulting in type inconsistency between columns in the source and destination databases.

  * If the data length in the destination database is shorter than that in the source database, data truncation may occur, resulting in data inconsistency between the source and destination databases.

* If you configure only **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.New.components.MigrationObjectForm.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for at least 7 days. Otherwise, the data migration task may fail due to the inability to obtain incremental logs, or data inconsistency may occur between the source and destination databases.

            // parallel_servers_target specifies the parallel query queuing conditions for each server.
            // For performance optimization, we recommend that you set this parameter to a value greater than the number of physical CPU cores, such as 1.5 times the number of physical CPU cores.             // _temporary_file_io_area_size specifies the file memory buffer limit.

         // parallel_servers_target specifies the parallel query queuing conditions for each server.
