# Migrate data between OceanBase Database Community Edition instances

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from one OceanBase Database Community Edition instance to another.

## Background information

You can create a data migration task in the OMS Community Edition console to migrate data from OceanBase Community Edition to OceanBase Community Edition. This task supports schema migration, full migration, and incremental synchronization to seamlessly migrate existing business data and incremental data from the source database to the destination database.

## Prerequisites

* You have created the corresponding schema in OceanBase Community Edition on the destination. OMS Community Edition supports migrating tables and columns. Therefore, you must create the corresponding schema in OceanBase Community Edition on the destination in advance.

* You have created database users for data migration tasks in OceanBase Community Edition on the source and destination, and granted the corresponding privileges to the users. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

* If you need to migrate tables without a primary key, create users and grant privileges to the users based on your business requirements before you create a data migration task. For more information, see [Create the __oceanbase_inner_drc_user user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* **Limitations on operations on the source database**

   **Do not execute DDL operations for changing the schema of a database or table during schema migration or full migration. Otherwise, the data migration task may fail.**

* In incremental synchronization scenarios, when `useTargetIndex = false`, **if a field of the BINARY type is used as the primary key or unique key in the destination database, and the length of the data to be migrated from the source database does not match the length of the BINARY field in the destination database, the UPDATE or DELETE operation cannot match the data, which may cause data quality issues.**

* Data source identifiers and user accounts must be globally unique in the OMS Community Edition system.

* OMS Community Edition does not support migrating internal tables whose names start with `__CTAS`.

* If temporary tables exist in OceanBase Community Edition versions earlier than V4.0.0, full migration fails.

* OMS Community Edition supports migrating databases, tables, and columns whose names contain only ASCII characters and do not include special characters (|"'`()=;/& and newline).

* OMS Community Edition supports migrating tables with and without a primary key in a single data migration task.

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If triggers exist in the destination, the data migration task may fail.

* OMS Community Edition does not support using OceanBase standby databases as the source.

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid affecting the running of data migration tasks.

* For OceanBase Database V4.x, we recommend that you enable log archiving. After log archiving is enabled, if a Clog is recycled, OMS can still perform incremental synchronization by consuming the archived logs. For more information, see [Log archiving](https://www.oceanbase.com/docs/community-observer-cn-10000000000901781).

* If the character set of the source database is UTF-8, we recommend that you use a character set that is compatible with the source character set (such as UTF-8 or UTF-16) for the destination database. Otherwise, garbled characters may appear in the destination database.

   For more information about garbled characters in the Latin1 character set, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* If the clocks of nodes or between a client and a server are not synchronized, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be positive.

* In data migration tasks between OceanBase Database V3.2.x and earlier versions, if the source database contains a multi-partition table with a global unique index, updating the values of the partitioning key of the table may result in data loss during data migration.

* Confirm whether the precision of the migration of columns of the DECIMAL, FLOAT, or DOUBLE type meets your expectations. If the precision of the destination column type is less than that of the source column type, truncation may occur, resulting in data inconsistency between the source and destination databases.

* If you change the unique index of the destination database without enabling DDL synchronization, you must restart the incremental synchronization component. Otherwise, data inconsistency may occur.

* If the data migration task does not enable forward switchover (which is not applicable to disaster recovery tasks), you must delete the unique index and pseudo column of the destination database. Otherwise, you cannot write data to the destination database, and the pseudo column will be regenerated when you import data to the downstream database, resulting in a conflict with the pseudo column of the source database.

   If the data migration task enables forward switchover, OMS Community Edition automatically deletes the hidden column and unique index based on the type of the data migration task. For more information, see [Hidden column mechanism](../600.data-migration/1600.migration-function-introduction/800.schema-migration-mechanisms.md).

* In the scenario of schema migration:

  * We recommend that you map the relationship between the source and destination databases by using an import object or matching rule.

  * We recommend that you manually create the table structure in the destination database. If you use OMS to create the table structure, skip failed objects in the schema migration step.

* In a data migration task from OceanBase Database to OceanBase Database with DDL synchronization enabled, if the source database tables are renamed, we recommend that you restart the task to avoid data loss during incremental synchronization.

* When you migrate data from OceanBase Database to OceanBase Database, the destination database objects are created in lowercase by default based on the parameter `lower_case_table_names = 1`.

* If the table structures of the source and destination databases are not identical, data inconsistency may occur. The following scenarios are known to cause data inconsistency:

  * If you manually create a table structure that is not supported by OMS Community Edition, implicit conversion may occur, resulting in column type inconsistency between the source and destination databases.

  * If the data length of the destination database is shorter than that of the source database, data truncation may occur, resulting in data inconsistency between the source and destination databases.

* If you configure only **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.components.SyncOption.CheckSyncKind.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for at least 7 days. Otherwise, the data migration task may fail because the incremental logs cannot be obtained, or data inconsistency may occur between the source and destination databases.

* If the value of `binlog_row_image` is not `FULL` when an application is started, OceanBase Database sets it to `FULL`. In this case, you must restart the application. Otherwise, OceanBase Database will miss log information, resulting in data synchronization issues in OMS Community Edition. The following command is used to set `binlog_row_image` to `FULL`:

   ```shell
   set global binlog_row_image = 'FULL';
   ```
