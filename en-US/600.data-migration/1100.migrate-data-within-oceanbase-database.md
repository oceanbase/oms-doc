# Migrate data between OceanBase Database Community Edition instances

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from an OceanBase Database Community Edition instance to another OceanBase Database Community Edition instance.

## Background information

You can create a data migration task in the OMS Community Edition console to migrate data from OceanBase Community Edition to OceanBase Community Edition. By using schema migration, full migration, and incremental synchronization, you can seamlessly migrate existing business data and incremental data from the source database to the destination database.

## Prerequisites

* You have created the corresponding schema in the destination OceanBase Community Edition database. OMS Community Edition supports table and column migration. Therefore, you must create the corresponding schema in the destination database.

* You have created dedicated database users for the source and destination OceanBase Community Edition databases and granted the required privileges to the users. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

* If you need to migrate tables without primary keys, create a user and grant the required privileges before you execute the data migration task. For more information, see [Create the __oceanbase_inner_drc_user user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* **Limitations on operations in the source database**

   **Do not perform DDL operations to change the schema of a database or table during schema migration or full migration. Otherwise, the data migration task may fail.**

* In incremental synchronization scenarios, **if the destination database uses a BINARY field as a primary key or unique key and the length of the BINARY field in the destination database is different from that in the source database, the UPDATE or DELETE operation cannot match the data, which may cause data quality issues.**

* Data source identifiers and user accounts must be globally unique in the OMS Community Edition system.

* OMS Community Edition does not support migrating internal tables whose names start with `__CTAS`.

* If the source database is an OceanBase Community Edition database of a version earlier than V4.0.0, the full migration task will fail if temporary tables exist.

* OMS Community Edition supports migrating databases, tables, and columns whose names are ASCII characters and do not contain special characters (spaces, line breaks, or |"'`()=;/&).

* OMS Community Edition supports migrating tables with and without primary keys in a single data migration task.

* If the destination database is a database, OMS Community Edition does not support triggers in the destination database. If triggers exist, the data migration task may fail.

* OMS Community Edition does not support using an OceanBase standby database as the source database.

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid affecting the running of the data migration task.

* For OceanBase Community Edition V4.x, we recommend that you enable log archiving. After log archiving is enabled, OMS Community Edition can still perform incremental synchronization by consuming the archived logs even if the Clog is recycled. For more information about how to enable log archiving, see [Log archiving documentation](https://www.oceanbase.com/docs/community-observer-cn-10000000000901781).

* If the source database uses the UTF-8 character set, we recommend that you use a character set that is compatible with the source database (such as UTF-8 or UTF-16) for the destination database to avoid garbled characters in the destination database.

   For more information about how to handle garbled characters when the source database uses the Latin1 character set, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* If the clocks of the nodes or the clocks of the client terminal and the server are out of sync, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be positive.

* In a data migration task between OceanBase Community Edition databases, if the source database is of a version earlier than V3.2.x and contains a multi-partition table with a global unique index, updating the value of the partitioning key of the table may cause data loss during the data migration.

* Verify whether the precision of the DECIMAL, FLOAT, or DOUBLE column type in the destination database meets the expected requirements. If the precision of the destination column type is less than that of the source column type, data truncation may occur, which may cause data inconsistency between the source and destination databases.

* If you modify the unique index of the destination database without enabling DDL synchronization, you must restart the incremental synchronization component to avoid data inconsistency.

* If the data migration task does not enable forward switchover (disaster recovery active-active scenarios do not have a forward switchover step), delete the unique index and pseudo column in the destination database. Otherwise, you cannot write data to the destination database, and pseudo columns will be generated again when you import data to downstream systems, which will conflict with the pseudo columns in the source database.

   If the data migration task enables forward switchover, OMS Community Edition automatically deletes the hidden columns and unique indexes based on the type of the data migration task. For more information, see [Hidden column mechanism of Data Transmission Service](../600.data-migration/1600.migration-function-introduction/800.schema-migration-mechanisms.md).

* In a database and table aggregation scenario:

  * We recommend that you map the relationship between the source and destination databases by using an imported object or matching rule.

  * We recommend that you manually create the table structure in the destination database. If you use OMS to create the table structure, skip some failed objects in the schema migration step.

* In a data migration task from an OceanBase Community Edition database that has synchronized DDL operations, if the source database or table is renamed (RENAME), we recommend that you restart the task to avoid data loss during incremental synchronization.

* When you migrate data from an OceanBase Community Edition database to another OceanBase Community Edition database, the destination database objects are created in lowercase by default based on the parameter `lower_case_table_names = 1`.

* If the table structures of the source and destination databases are not completely consistent, data inconsistency may occur. The following scenarios are known to cause data inconsistency:

  * When you manually create a table structure that exceeds the supported scope of OMS Community Edition, implicit conversion may cause the column types of the source and destination databases to be inconsistent.

  * If the length of the data in the destination database is shorter than that in the source database, data truncation may occur, which may cause data inconsistency between the source and destination databases.

* If you only configure **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the source database must retain local incremental logs for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.components.SyncOption.CheckSyncKind.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the source database must retain local incremental logs for at least 7 days. Otherwise, the data migration task may fail because the incremental logs cannot be obtained, or data inconsistency may occur between the source and destination databases.

* If the `binlog_row_image` parameter is not set to `FULL` when an application is started, OceanBase Community Edition sets it to `FULL`. You must restart the application. Otherwise, OceanBase Community Edition will miss log information, which will cause data synchronization issues in OMS Community Edition. The following command is used to set the parameter:

   ```shell
   set global binlog_row_image = 'FULL';
   ```

      |Handling Strategy When Target Objects Exist|The value can be **<UI-TERM key="oms-community.Operation.constants.Ignore">Ignore</UI-TERM>** or **<UI-TERM key="oms-community.New.components.ParameterForm.StopProject">Stop Migration</UI-TERM>**:<ul><li>If you select **<UI-TERM key="oms-community.New.components.ParameterForm.Ignore">Ignore</UI-TERM>**, OMS Community Edition records the conflicting data in the log and retains the original data when the target table contains data that conflicts with the data to be written. <main id="notice" type='notice'><h4>Notice</h4><p>If you select <b>Ignore</b>, full verification will pull data in IN mode and cannot verify scenarios where the target has data that the source does not.       If index post-creation is allowed, we recommend that you adjust the parameters based on the hardware conditions of OceanBase Database Community Edition and the current business traffic.

      * If you use OceanBase Database Community Edition V4.x, you can use the black screen client tool to adjust the following sys tenant parameters and business tenant parameters.

        * Adjust the sys tenant parameters

            ```sql
            // parallel_servers_target specifies the parallel query queuing conditions on each server.
            // For better performance, we recommend that you set this parameter to a value greater than the number of physical CPU cores, such as 1.5 times the number of physical CPU cores. The value cannot exceed 64 to avoid lock contention in the OceanBase Database Community Edition kernel.
            set global parallel_servers_target = 64;
            ```

        * Adjust the business tenant parameters

            ```sql
            // File memory buffer limit
            alter system set _temporary_file_io_area_size = '10' tenant = 'xxx';
            // Disable throttling in 4.x
            alter system set sys_bkgd_net_percentage = 100;
            ```

      * If you use OceanBase Database Community Edition V3.x, you can use the black screen client tool to adjust the following sys tenant parameters.

         ```sql
         // parallel_servers_target specifies the conditions under which parallel queries are queued on each server.
         // For performance, we recommend that you set this parameter to a value greater than the number of physical CPUs, such as 1.5 times that value. However, the parameter value must be less than or equal to 64 to avoid kernel locking issues in OceanBase Database Community Edition.
         set global parallel_servers_target = 64;
         // data_copy_concurrency  specifies the maximum number of data migration and replication tasks that can be executed in the system concurrently.
         alter system set data_copy_concurrency = 200;
         ```

   In the **<UI-TERM key="oms-community.SystemParam.contants.Precheck">Precheck</UI-TERM>** step, OMS Community Edition checks whether the read and write permissions of the database user and the network connection to the database meet the requirements.
