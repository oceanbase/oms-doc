# Migrate data from a MySQL database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a MySQL database to OceanBase Database Community Edition.

## Background information

You can create a data migration task in the OMS Community Edition console to migrate data from a self-managed MySQL database to OceanBase Database Community Edition. This task allows you to seamlessly migrate existing business data and incremental data from the source database to OceanBase Database Community Edition through schema migration, full data migration, and incremental synchronization.

MySQL databases support various modes, including single primary database, single standby database, and primary-standby database. The supported operations vary depending on the type of data source during migration to OceanBase Database Community Edition.

| Type  |                          Supported operations                           |
|-----|----------------------------------------------------------|
| Single primary database | Schema migration + Full data migration + Incremental synchronization + Full data verification + Reverse incremental synchronization |
| Single standby database | Schema migration + Full data migration + Incremental synchronization + Full data verification |
| Primary-standby database | Primary database (database connects to the primary database): Reverse incremental synchronization is supported. <br>Standby database (database connects to the standby database): Schema migration + Full data migration + Incremental synchronization + Full data verification <br>When the source is **<UI-TERM key="oms-community.Endpoint.Detail.PrimaryDatabaseAndSecondaryDatabase">Primary Database + Standby Database</UI-TERM>**, if you configure incremental synchronization and reverse incremental synchronization, the database connects to the primary database. If you configure schema migration, full data migration, incremental synchronization, and full data verification, the database connects to the standby database.  |

## Prerequisites

* You have enabled Binlog for the self-managed MySQL database. For more information, see [Enable Binlog for the MySQL database](../800.create-and-manage-data-sources/500.enable-binlogs-for-the-mysql-database.md).

* You have created dedicated database users for the source self-managed MySQL database and OceanBase Database Community Edition, and granted the required privileges to the users. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* **Limitations on operations on the source database**

   **Do not perform DDL operations to change the schema of the source database or table during schema migration or full data migration. Otherwise, the data migration task may be interrupted.**

* The supported MySQL database versions are V5.5, V5.6, V5.7, and V8.0. OMS Community Edition supports the InnoDB, TokuDB, XENGINE, and RocksDB storage engines for MySQL databases. Other storage engines do not support data migration.

* Out-of-band import does not support writing data in the Latin1 character set. An exception will be thrown.

* If the primary key is of the FLOAT or DOUBLE type, the pre-check will fail. We strongly recommend that you do not use this type as the primary key.

* If the destination is a database, OMS Community Edition does not support triggers on the destination. If triggers exist, data migration may fail.

* OMS Community Edition does not support migrating index fields in MySQL databases that exceed 767 bytes (191 characters).

* Data source identifiers and user accounts must be globally unique within the OMS Community Edition system.

* OMS Community Edition supports migrating databases, tables, and columns that have ASCII-compliant names without special characters (including line breaks, spaces, and |"'`()=;/&).

* If the `lower_case_table_names` settings of the source and destination databases are inconsistent, you cannot create a task. Additionally, OMS Community Edition does not support case-sensitive settings for MySQL databases and OceanBase Database. If both the source and destination are set to `lower_case_table_names=0`, you cannot create a task.

   By default, the destination database objects are created in lowercase based on the `lower_case_table_names = 1` parameter.

* OMS Community Edition does not support migrating cascade foreign keys from the source MySQL database.

* Ensure that the clocks of the source and destination databases are synchronized.

## Considerations

* We recommend that you migrate no more than 1,000 tables in one go. Otherwise, the data migration task may fail.

* The MySQL database host must have sufficient outbound bandwidth. Otherwise, the log parsing and data migration may be affected, which may result in synchronization latency.

* If the collations of the source and destination databases are different:

  * Data synchronization may be inconsistent. For example, if the source database uses the utf8mb4_0900_ai_ci collation and the destination database uses the utf8mb4_general_ci collation, the data 'A' and 'A ' in the source database may not be written to the destination database, which may result in data loss.

  * The data verification of tables with the VARCHAR type as the primary key may be inconsistent.

* If the source database uses the Latin1 character set, for information about how to handle garbled characters, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* If the clocks of the nodes or the client and server are not synchronized, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be inaccurate.

* If incremental parsing is required for the MySQL database, the `server_id` parameter must be set for the source MySQL server.

* If you change the unique index of the destination database without enabling DDL synchronization, you must restart the incremental synchronization component. Otherwise, data inconsistency may occur.

* In reverse incremental migration from a MySQL database to OceanBase Database Community Edition, if the destination database is an earlier version than V3.2.x and has a global unique index, data may be lost during migration when you update the partition key values.

* Verify whether the migration precision of the DECIMAL, FLOAT, and DOUBLE column types meets your expectations in OceanBase Database Community Edition. If the precision of a destination column is less than that of the corresponding source column, the data may be truncated, which may result in data inconsistency between the source and destination databases.

* In the scenario of database and table aggregation:

  * We recommend that you map the relationships between the source and destination databases by using import objects or matching rules.

  * We recommend that you create the table structure in the destination database. If you use OceanBase Database Community Edition to create the table structure, skip the failed objects in the structure migration step.

* OceanBase Database Community Edition supports different numbers of columns in the source and destination databases. If an error is returned indicating that a column in the source database does not exist in the destination database during full migration or incremental synchronization, you can set the `ignoreRedunantColumnsReplicate` parameter of the **full-Import** or **Incr-Sync** component to `true` and resume the data migration task.

* If the table structures of the source and destination databases are not completely consistent, data inconsistency may occur. The following are known scenarios:

  * If the user manually creates a table structure that exceeds the supported scope of OceanBase Database Community Edition, implicit conversion may occur, resulting in type inconsistency between the columns of the source and destination databases.

  * If the length of the data in the destination database is shorter than that in the source database, the data may be truncated, which may result in data inconsistency between the source and destination databases.

* If the MySQL database is a dual-master or multi-master database, you must enable the `log_slave_updates` parameter. Otherwise, data loss may occur because the data source does not receive all Binlogs.

* If you configure only **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.New.components.MigrationObjectForm.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.components.SyncOption.CheckSyncKind.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for at least 7 days. Otherwise, the data migration task may fail because the incremental logs cannot be obtained, which may result in data inconsistency between the source and destination databases.

* If the MySQL database is a dual-master or multi-master database, you must enable the `log_slave_updates` parameter. Otherwise, data loss may occur because the data source does not receive all Binlogs.
