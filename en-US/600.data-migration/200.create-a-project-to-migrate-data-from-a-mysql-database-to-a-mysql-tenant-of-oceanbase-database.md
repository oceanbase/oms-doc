# Migrate data from a MySQL database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a MySQL database to OceanBase Database Community Edition.

## Background information

You can create a data migration task in the OMS Community Edition console to migrate data from a self-managed MySQL database to OceanBase Database Community Edition. You can perform schema migration, full data migration, and incremental synchronization to seamlessly migrate existing business data and incremental data from the source database to OceanBase Database Community Edition.

MySQL databases support various modes, including single primary database, single standby database, and primary-standby database. The operations supported for different types of data sources vary when you migrate data from a MySQL database to OceanBase Database Community Edition.

| Type  |                          Supported operations                           |
|-----|----------------------------------------------------------|
| Single primary database | Schema migration + full data migration + incremental synchronization + full data verification + reverse incremental synchronization                          |
| Single standby database | Schema migration + full data migration  + incremental synchronization + full data verification                                      |
| Primary-standby database | Primary database (the database is connected to the primary database): Reverse incremental synchronization is supported. <br>Standby database (the database is connected to the standby database): Schema migration + full data migration + incremental synchronization + full data verification <br>When the source is **<UI-TERM key="oms-community.Endpoint.Detail.PrimaryDatabaseAndSecondaryDatabase">Primary Database + Standby Database</UI-TERM>**, if you configure incremental synchronization and reverse incremental synchronization, the database is connected to the primary database. If you configure schema migration, full data migration, incremental synchronization, and full data verification, the database is connected to the standby database.  |

## Prerequisites

* You have enabled Binlog for the self-managed MySQL database. For more information, see [Enable Binlog for a MySQL database](../800.create-and-manage-data-sources/500.enable-binlogs-for-the-mysql-database.md).

* You have created a database user for the data migration task in the source self-managed MySQL database and OceanBase Database Community Edition, and granted the necessary privileges to the user. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* **Limitations on operations in the source database**

   **Do not perform DDL operations to change the schema of a database or table during schema migration or full data migration. Otherwise, the data migration task may fail.**

* The supported MySQL database versions are V5.5, V5.6, V5.7, and V8.0. OMS Community Edition supports the InnoDB, TokuDB, and XENGINE storage engines for MySQL databases. Data migration is not supported for other storage engines.

* The direct load feature does not support writing data in the Latin1 character set. An exception will be thrown.

* If the primary key is of the FLOAT or DOUBLE type, the precheck will fail. We recommend that you do not use this type as the primary key.

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If a trigger exists, the data migration task may fail.

* OMS Community Edition does not support migrating index fields that exceed 767 bytes (191 characters) in length from a MySQL database.

* Data source identifiers and user accounts must be globally unique within the OMS Community Edition system.

* OMS Community Edition supports migrating databases, tables, and columns whose names are ASCII characters and do not contain special characters (including line breaks, spaces, and |"'`()=;/&).

* If the `lower_case_table_names` parameter is set to different values in the source and destination, you cannot create a data migration task. OMS Community Edition does not support case-sensitive settings for MySQL databases and OceanBase Database. If the `lower_case_table_names` parameter is set to `0` in both the source and destination, you cannot create a data migration task.

   By default, the `lower_case_table_names` parameter is set to `1` in the destination, and database objects are created in lowercase.

* OMS Community Edition does not support migrating cascade foreign keys from a MySQL database.

* Make sure that the clocks of the source and destination databases are synchronized.

## Considerations

* We recommend that you migrate no more than 1000 tables at a time to avoid affecting the running of the data migration task.

* The host of the source MySQL database must have sufficient outbound bandwidth. If the outbound bandwidth is insufficient, the log parsing and data migration speed will be affected, which may result in synchronization delay.

* If the collations of the source and destination databases are different:

  * Data synchronization may be inconsistent. For example, if the source database is of the utf8mb4_0900_ai_ci collation and the destination database is of the utf8mb4_general_ci collation, the data 'A' and 'A ' in the source database may not be written to the destination database, which may result in data loss.

  * Data verification for tables with the VARCHAR type as the primary key may be inconsistent.

* If the character set of the source database is Latin1, for more information about garbled characters, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* If the clocks of the nodes or the clocks of the client and server are out of sync, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be inaccurate.

* If incremental parsing is required for the MySQL database, the `server_id` parameter must be set for the source MySQL Server.

* If you modify the unique index of the destination database without enabling DDL synchronization, you must restart the incremental synchronization component to avoid data inconsistency.

* In reverse incremental migration from a MySQL database to OceanBase Database Community Edition, if the destination database is of a version earlier than V3.2.x and contains a multi-partition table with a global unique index, modifying the value of the partition key of the table may result in data loss during data migration.

* Verify whether the precision of the DECIMAL, FLOAT, and DOUBLE column types is migrated as expected in OceanBase Database Community Edition. If the precision of the destination column type is less than that of the source column type, truncation may occur, resulting in data inconsistency between the source and destination databases.

* In the scenario where tables are aggregated:

  * We recommend that you map the relationships between the source and destination databases by using import objects or matching rules.

  * We recommend that you create the table structure in the destination database. If you use OMS Community Edition to create the table structure, skip failed objects in the structure migration step.

* OMS Community Edition allows the number of fields in the source and destination databases to be inconsistent. If an error indicating that the fields in the source table do not exist in the destination database is returned during full migration or incremental synchronization, you can set the `ignoreRedunantColumnsReplicate` parameter of the **full-Import** or **Incr-Sync** component to `true` to resume the data migration task.

* If the table structures of the source and destination databases are inconsistent, data inconsistency may occur. The following are known scenarios:

  * If the user manually creates a table structure that exceeds the supported scope of OMS Community Edition, implicit conversion may occur, resulting in type inconsistency between the columns of the source and destination databases.

  * If the length of the data in the destination database is shorter than that in the source database, data truncation may occur, resulting in data inconsistency between the source and destination databases.

* If the source MySQL database is of a dual-master or multi-master architecture, set the `log_slave_updates` parameter to avoid data loss caused by the data source not receiving all Binlogs.

* If you configure only **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.New.components.MigrationObjectForm.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.components.SyncOption.CheckSyncKind.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for at least 7 days. Otherwise, the data migration task may fail because the incremental logs cannot be obtained, or data inconsistency may occur between the source and destination databases.

* If the source MySQL database is of a dual-master or multi-master architecture, set the `log_slave_updates` parameter to avoid data loss caused by the data source not receiving all Binlogs.

      * If you use OceanBase Database Community Edition V4.x, you can use a CLI tool to adjust the following sys tenant parameters and business tenant parameters.

        * Adjust the sys tenant parameters

            ```sql
            // parallel_servers_target specifies the parallel query queuing condition on each server.
            // For optimal performance, we recommend that you set this parameter to a value greater than the number of physical CPU cores, such as 1.5 times the number of physical CPU cores. The value should not exceed 64 to avoid lock contention in the OceanBase Database Community Edition kernel.
            set global parallel_servers_target = 64;
            ```

        * Adjust the business tenant parameters

            ```sql
            // File memory buffer limit
            alter system set _temporary_file_io_area_size = '10' tenant = 'xxx';
            // Disable throttling in 4.x
            alter system set sys_bkgd_net_percentage = 100;
            ```

      * If you use OceanBase Database Community Edition V3.x, you can use a CLI tool to adjust the following sys tenant parameters.

         ```sql
         // parallel_servers_target specifies the number of parallel queries allowed on each server.
         // To improve performance, we recommend that you set the value of this parameter to a value greater than the number of physical CPUs, for example, 1.5 times the number of physical CPUs. However, we recommend that you do not set the value greater than 64 to avoid the lock contention issue in the OceanBase Database Community Edition kernel.
         set global parallel_servers_target = 64;
         // data_copy_concurrency  specifies the maximum number of data migration replication tasks that can be concurrently executed in the system.
         alter system set data_copy_concurrency = 200;
         ```
