# Migrate data from a TiDB database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a TiDB database to OceanBase Database Community Edition.

## Background information

OMS Community Edition allows you to create a data migration task to migrate data from a source TiDB database to OceanBase Community Edition. You can seamlessly migrate existing business data and incremental data from the source database to OceanBase Community Edition by using schema migration, full migration, and incremental synchronization.

TiDB is a hybrid transactional and analytical processing (HTAP) database that supports online transaction processing (OLTP) and online analytical processing (OLAP). If you need to perform incremental synchronization, select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source.

If you select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source, you must deploy a TiCDC cluster and a Kafka cluster to synchronize incremental data from the TiDB database to OceanBase Community Edition. If incremental synchronization is not selected for the data migration task, you do not need to deploy a TiCDC cluster and a Kafka cluster.

![architecture8-zh](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oms/oms-enterprise/architecture8-zh.png)

TiCDC is an incremental data synchronization tool for the TiDB database. It achieves high availability by using a PD cluster, which is the scheduling module of a TiDB cluster, usually consisting of three PD nodes. A TiKV server is a TiKV node in a TiDB cluster. It actively sends change data to the TiCDC cluster in the form of change logs. The TiCDC tool obtains data from multiple TiCDC processes, processes the data, and synchronizes the data to the Kafka cluster. The Kafka cluster stores the incremental logs of the TiDB database converted by the TiCDC tool. This way, OMS Community Edition can obtain the corresponding data from the Kafka cluster and synchronize the data to OceanBase Community Edition in real time.

## Prerequisites

You have created a database user for the source TiDB database and OceanBase Community Edition and granted the necessary permissions to the user. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* The supported TiDB database versions are V2.x, V3.x, V4.x, V5.x, V6.x, V7.x, and V8.x. The supported Kafka versions are V0.9, V1.0, V2.x, V3.x, and V4.x.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>TiDB databases of versions V2.x and V3.x support only TiDB Binlog. </p>
   </main>

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If triggers exist, the data migration task may fail.

* DDL synchronization is not supported when you migrate data from the TiDB database to OceanBase Community Edition.

* Incremental synchronization from the TiDB database to OceanBase Community Edition is not supported for tables without a primary key.

* Data source identifiers and user accounts must be globally unique in the OMS system.

* OMS Community Edition supports only objects whose names are ASCII characters and do not contain special characters (spaces, line breaks, or |"'`()=;/&).

* OMS Community Edition supports only the TiCDC Open Protocol. If you use other protocols, an error will be returned because the JDBC-Connector will be null.

* Make sure that the `enable-old-value=true` parameter is added to the TiCDC configuration when you synchronize data to Kafka. Otherwise, an error will be returned because the data synchronization message format is incorrect. For more information, see [Description of the synchronization task configuration file](https://docs-archive.pingcap.com/zh/tidb/v4.0/manage-ticdc#%E5%90%8C%E6%AD%A5%E4%BB%BB%E5%8A%A1%E9%85%8D%E7%BD%AE%E6%96%87%E4%BB%B6%E6%8F%8F%E8%BF%B0).

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid affecting the migration task.

* If the source database contains foreign keys with the same name, an error will be returned during schema migration. You can modify the foreign key constraint name and then resume the task.

* If the source database uses the UTF-8 character set, we recommend that you use a compatible character set (such as UTF-8 or UTF-16) for the destination database to avoid garbled characters in the destination database.

   For more information about garbled characters in the Latin1 character set, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* When you perform reverse incremental migration from a TiDB database to OceanBase Database Community Edition, if the destination database is earlier than V3.2.x and contains a multi-partition table with a global unique index, data loss may occur during migration if you update the partition key values of the table.

* Do not write data to a topic used for TiCDC synchronization, or a null pointer exception will be returned.

* Make sure that the precision of the DECIMAL, FLOAT, or DOUBLE column types is migrated as expected. If the precision of the destination column type is less than that of the source column type, truncation may occur, resulting in data inconsistency between the source and destination.

* If you modify the unique index of the destination database, you must restart the incremental synchronization component to avoid data inconsistency.

* If the clocks of the nodes or the client and server are out of sync, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be inaccurate.

* In the scenario where multiple tables are migrated:

  * We recommend that you use import objects or matching rules to map the relationships between the source and destination databases.

  * We recommend that you create the table structure in the destination database. If you use OMS to create the table structure, skip the failed objects during schema migration.

* If the table structures of the source and destination databases are not completely consistent, data inconsistency may occur. The following scenarios are known:

  * If you manually create a table structure that is not supported by OMS Database Community Edition, implicit conversion may occur, resulting in type inconsistency between the source and destination columns.

  * If the length of the destination data is less than that of the source data, data truncation may occur, resulting in data inconsistency between the source and destination.

* When you use TiDB Database V2.x, V3.x, or V4.x, note the following issues. For more information about TiDB Binlog, see [TiDB Binlog](https://docs.pingcap.com/zh/tidb/stable/tidb-binlog-overview).

  * TiDB Binlog does not support heartbeat packets. If no updates are performed on the source database, the incremental data position will not be updated.

  * Before incremental synchronization starts, the source database must have updates. Otherwise, an error `data not existed` will be returned.

  * For tables without a primary key, the incremental Binlog cannot obtain information about other unique keys. In the program, all fields are treated as primary keys. When updates are synchronized from the source to the destination, the update is first deleted and then inserted.

  * If you set `source.cdcDataFormat=tidbBinlog` for the Incr-Sync component, you can use the `tidbBinlog` data format.

* If you configure only **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the source database must save local incremental logs for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the source database must save local incremental logs for at least 7 days. Otherwise, the data migration task may fail because it cannot obtain incremental logs, or data inconsistency may occur between the source and destination.

The value must not exceed 64, to avoid the core lock contention issue in OceanBase Database Community Edition.
            set global parallel_servers_target = 64;
            ```

            ```

      * If you are using OceanBase Database Community Edition V3.x, you can adjust the following sys tenant parameters by using the CLI.

9. Click **<UI-TERM key="oms-community.SystemParam.contants.Precheck">Precheck</UI-TERM>**. The system performs a precheck on the data migration task.

   In the **<UI-TERM key="oms-community.Sync.New.Precheck">Precheck</UI-TERM>** step, OMS Community Edition checks whether the read and write permissions of the database user and the network connection of the database meet the requirements. You can start a data migration task only after all the precheck tasks are completed. If an error is reported during the precheck:

   * You can troubleshoot and fix the error, and then perform the precheck again until the precheck is successful.

   * You can also click **<UI-TERM key="must.AlertTips.commponents.ErrorDetail.Skip">Skip</UI-TERM>** in the Actions column of the error item. A dialog box pops up to prompt you of the impact of skipping this operation. After you confirm that you can skip this operation, click **<UI-TERM key="oms-community.Migration.hooks.useMigrationObject.Determine">OK</UI-TERM>** in the dialog box.

You can manually start the task as needed.

After the data migration task is started, the system executes the task based on the migration type you selected.
