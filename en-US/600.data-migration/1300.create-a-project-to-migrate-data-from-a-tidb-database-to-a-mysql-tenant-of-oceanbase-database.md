# Migrate data from a TiDB database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a TiDB database to OceanBase Database Community Edition.

## Background information

The OMS Community Edition allows you to create a data migration task to migrate data from a source TiDB database to a target OceanBase Community Edition database. You can seamlessly migrate the business data and incremental data from the source database to OceanBase Community Edition by using schema migration, full migration, and incremental synchronization.

TiDB Database is a hybrid transactional and analytical processing (HTAP) database that supports online transaction processing and online analysis processing.

* If you use TiDB Database V4.x or later, and select **<UI-TERM key="oms-community.Endpoint.constants.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source, you must deploy a TiCDC cluster and a Kafka cluster to synchronize incremental data from TiDB Database to OceanBase Community Edition.

   ![architecture8-zh](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oms/oms-enterprise/architecture8-zh.png)

   TiCDC is a tool for synchronizing incremental data from TiDB Database. The PD cluster, which is used for scheduling in the TiDB cluster and typically consists of three PD nodes, ensures the high availability of the TiDB Database. The TiKV server, which is a node in the TiDB cluster, sends change data to the TiCDC cluster in the form of change logs. The TiCDC tool synchronizes data from the TiKV node to the Kafka cluster through multiple TiCDC processes after the data is processed. The Kafka cluster stores the incremental logs converted by the TiCDC tool from the TiDB Database, so that OMS can obtain the data from the Kafka cluster and migrate it to OceanBase Community Edition in real time during incremental data synchronization.

* If you use TiDB Database V4.x or later, you can create a TiDB data source without selecting **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** to synchronize incremental data from TiDB Database to OceanBase Community Edition.

## Prerequisites

You have created dedicated database users in the source TiDB database and the target OceanBase Community Edition database for the data migration task and granted corresponding privileges to the users. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* At present, TiDB Database V2.x, V3.x, V4.x, V5.x, V6.x, and V7.x are supported.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>TiDB Database V2.x and V3.x support only TiDB Binlog. </p>
   </main>

* If the target is a database, the OMS Community Edition does not support triggers in the target database. If triggers exist in the target database, the data migration may fail.

* DDL synchronization is not supported during data migration from TiDB Database to OceanBase Community Edition.

* The OMS Community Edition does not support the migration of tables without primary keys or data containing spaces to OceanBase Community Edition.

* Data source identifiers and user accounts must be globally unique in OMS.

* OMS only supports migrating databases, tables, and column objects with ASCII-compliant names that do not contain special characters (spaces, |"'`()=;/&-).

* The OMS Community Edition supports only the TiCDC open protocol. If you use any other protocol, a Java Database Connectivity-Connector (JDBC-Connector) exception will occur, and a null pointer exception will be reported.

* Make sure to add enable-old-value = true when you configure the settings for synchronizing data from TiCDC to the Kafka cluster. Otherwise, the message format of data synchronization may be abnormal. For more information, see [Description of synchronization tasks](https://docs-archive.pingcap.com/zh/tidb/v4.0/manage-ticdc#%E5%90%8C%E6%AD%A5%E4%BB%BB%E5%8A%A1%E9%85%8D%E7%BD%AE%E6%96%87%E4%BB%B6%E6%8F%8F%E8%BF%B0).

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid impacting the data migration task.

* If there are foreign keys with the same name in the source, an error is reported during schema migration. You can change the name of the foreign key constraint and resume the task.

* If the source character set is UTF-8, we recommend that you use a compatible character set as the target character set, such as UTF-8 or UTF-16, to avoid issues like garbled text in the target due to character set incompatibility.

* During reverse incremental migration from a TiDB database to OceanBase Community Edition V3.2.x or earlier, if the source table is a multi-partition table with a global unique index and you update the values of the partitioning key, data may be lost during migration.

* Do not write data to the topic synchronized by TiCDC. Otherwise, the JDBC-Connector may fail with an error indicating a null pointer exception.

* Make sure that the migration precision for columns of the DECIMAL, FLOAT, or DOUBLE data type meets your requirements in OMS Community Edition. If the precision of the target column type is less than that of the source column type, the data may be truncated, leading to inconsistent data between the source and target.

* If you change the unique index of the target, you must restart the incremental synchronization component. Otherwise, the data may be inconsistent.

* If the clocks between nodes or between the client and the server are out of synchronization, the latency may be inaccurate during incremental synchronization or reverse incremental migration.

   For example, if the clock is earlier than the standard time, the latency can be negative. If the clock is later than the standard time, the latency can be positive.

* Take note of the following points if you want to perform data deduplication:

  * We recommend that you map the schemas of the source and target databases by using schema objects or matching rules.

  * We recommend that you manually create schemas in the target database. If you use OMS to create schemas, skip failed objects in the schema migration step.

* A difference between the source and target table schemas may result in inconsistent data. Some known scenarios are described as follows:

  * When you manually create a table schema in the target database, it may exceed the support scope of OMS Community Edition, which can lead to implicit data type conversion and inconsistent column types between the source and target.

  * If the length of a column in the target database is shorter than that in the source database, the data in this column may be truncated, resulting in inconsistent data between the source and target.

* Take note of the following points if you want to migrate data from a TiDB database of a version earlier than V4.0:

  * TiDB Binlog does not send heartbeats. If no updates are made in the source, the data change watermark does not advance.

  * If no updates are made in the source before the start of incremental synchronization, the task will fail with the error code `data not existed`.

  * For a table without a primary key, other unique keys (UKs) cannot be obtained from incremental logs. In the program, all fields are treated as the UK. When an update operation is performed on the source table, it is deleted and then inserted in the target table.

* If you select only **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs in the source database must be retained for more than 48 hours.

   ​​​If you select **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs in the source database must be retained for at least seven days. Otherwise, the data migration task may fail or the data in the source and target databases may be inconsistent because OMS cannot obtain incremental logs.

   In the **<UI-TERM key="oms-community.Sync.New.Precheck">Precheck</UI-TERM>** step, OMS Community Edition checks whether the database user has the required read/write permissions and whether the database connection is normal. The data migration task will not start unless all checks pass. If the precheck fails:

   * You can troubleshoot the issues and re-run the precheck until it succeeds.

   * You can also click **<UI-TERM key="must.AlertTips.commponents.ErrorDetail.Skip">Skip</UI-TERM>** in the operation column of the failed precheck item. A dialog box will appear, showing the impact of skipping the operation. You can start the task later as needed.
