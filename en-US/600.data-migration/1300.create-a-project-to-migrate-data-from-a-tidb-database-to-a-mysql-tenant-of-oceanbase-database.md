# Migrate data from a TiDB database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a TiDB database to OceanBase Database Community Edition.

## Background information

OMS Community Edition allows you to migrate data from a source TiDB database to a destination OceanBase Database Community Edition. You can seamlessly migrate existing business data and incremental data from the source database to OceanBase Database Community Edition by using schema migration, full data migration, and incremental synchronization.

TiDB is a hybrid transactional/analytical processing (HTAP) database that supports online transaction processing (OLTP) and online analytical processing (OLAP). If you use a TiDB database of a version earlier than V4.x, select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source. If you use a TiDB database of V4.x or later, you can skip this step and directly use OMS Community Edition to synchronize incremental data from the TiDB database.

If you select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source, you must deploy a TiCDC cluster and a Kafka cluster to synchronize incremental data from the TiDB database to OceanBase Database Community Edition. If the data migration task does not require incremental synchronization, you do not need to deploy a TiCDC cluster and a Kafka cluster.

![architecture8-zh](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oms/oms-enterprise/architecture8-zh.png)

TiCDC is an incremental data synchronization tool for TiDB. It ensures high availability by using a PD cluster, which consists of three PD nodes. TiKV Server is a TiKV node in a TiDB cluster. It actively sends change data to the TiCDC cluster in the form of change logs. The TiCDC tool obtains data from multiple TiCDC processes, processes the data, and synchronizes the data to the Kafka cluster. The Kafka cluster stores the incremental logs of the TiDB database converted by the TiCDC tool, so that OMS Community Edition can obtain the corresponding data from the Kafka cluster and synchronize the data to OceanBase Database Community Edition in real time.

## Prerequisites

You have created a database user for data migration tasks in the source TiDB database and OceanBase Database Community Edition, and granted the required permissions to the database user. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* The supported TiDB database versions are V2.x, V3.x, V4.x, V5.x, V6.x, V7.x, and V8.x. The supported Kafka versions are V0.9, V1.0, V2.x, V3.x, and V4.x.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>TiDB databases of versions earlier than V4.x support only TiDB Binlog. </p>
   </main>

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If a trigger exists, data migration may fail.

* When you migrate data from a TiDB database to OceanBase Database Community Edition, DDL operations are not synchronized.

* OMS Community Edition does not support migrating tables without a primary key or tables containing spaces from a TiDB database to OceanBase Database Community Edition.

* Data source identifiers and user accounts must be globally unique in the OMS system.

* OMS Community Edition supports only migrating databases, tables, and columns whose names are in ASCII and do not contain special characters (|"'`()=;/& and line breaks).

* OMS Community Edition supports only the TiCDC Open Protocol. If you use a different protocol, an exception occurs in the JDBC-Connector, and a null pointer error is returned.

* Make sure that the `enable-old-value=true` parameter is added to the TiCDC synchronization configuration to the Kafka cluster. Otherwise, the data synchronization message format may be abnormal. For more information, see [Description of synchronization task configuration files](https://docs-archive.pingcap.com/zh/tidb/v4.0/manage-ticdc#%E5%90%8C%E6%AD%A5%E4%BB%BB%E5%8A%A1%E9%85%8D%E7%BD%AE%E6%96%87%E4%BB%B6%E6%8F%8F%E8%BF%B0).

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid affecting the running of the data migration task.

* If the source database contains foreign keys with the same name, an error will be returned during schema migration. You can modify the name of the foreign key constraint and then resume the task.

* If the source database uses the UTF-8 character set, we recommend that you use a character set that is compatible with the source database character set (such as UTF-8 or UTF-16) for the destination database to avoid garbled characters in the destination database.

   For more information about garbled characters in the Latin1 character set, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* During reverse incremental synchronization from a TiDB database to OceanBase Database Community Edition, if OceanBase Database Community Edition is earlier than V3.2.x and the table has a global unique index, updating the partition key values may result in data loss during the synchronization.

* Do not write data to the topic used for synchronization by TiCDC, otherwise, an exception will be returned and a null pointer error will be reported.

* Verify whether the precision of the DECIMAL, FLOAT, or DOUBLE column types in the destination database is consistent with that in the source database. If the precision of the destination column type is smaller than that of the source column type, truncation may occur, resulting in data inconsistency between the source and destination databases.

* If you modify the unique index in the destination database, you must restart the incremental synchronization component. Otherwise, data inconsistency may occur.

* If the clocks of the nodes or the client and server are out of sync, the delay (incremental synchronization or reverse incremental synchronization) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be positive.

* In the scenario where tables are aggregated:

  * We recommend that you use an import object or matching rules to map the relationships between the source and destination databases.

  * We recommend that you create the table structure in the destination database. If you use OMS to create the table structure, skip the failed objects in the schema migration step.

* If the table structures in the source and destination databases are not completely consistent, data inconsistency may occur. The following are known scenarios:

  * When you manually create the table structure, if the structure exceeds the supported scope of OMS Community Edition, implicit conversion may occur, resulting in type inconsistency between the columns in the source and destination databases.

  * If the length of the data in the destination database is shorter than that in the source database, truncation may occur, resulting in data inconsistency between the source and destination databases.

* When you use TiDB Database V2.x, V3.x, or V4.x, note the following issues. For more information about TiDB Binlog, see [TiDB Binlog](https://docs.pingcap.com/zh/tidb/stable/tidb-binlog-overview).

  * TiDB Binlog does not support heartbeat packets. If no updates occur in the source database, the incremental data checkpoint will not be updated.

  * Before incremental synchronization starts, the source database must have updates. Otherwise, an error `data not existed` will be returned.

  * For tables without a primary key, the incremental Binlog cannot obtain information about other unique keys. In this case, all fields are treated as the primary key. When updates in the source database are synchronized to the destination database, the updates are first deleted and then inserted.

  * If you set the `source.cdcDataFormat` parameter to `tidbBinlog` for the Incr-Sync component, you can use the `tidbBinlog` data format.

* If you only configure **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the data migration task requires that the local incremental logs of the source database be retained for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the data migration task requires that the local incremental logs of the source database be retained for at least 7 days. Otherwise, the data migration task may fail because it cannot obtain incremental logs, or data inconsistency may occur between the source and destination databases.

            ```sql
            // For performance optimization, we recommend that you set this parameter to a value greater than the number of physical CPU cores, such as 1.5 times the number of physical CPU cores. However, the value must not exceed 64 to avoid lock contention in the OceanBase Database Community Edition kernel.
            set global parallel_servers_target = 64;
            ```

   In the **<UI-TERM key="oms-community.Sync.New.Precheck">Precheck</UI-TERM>** section, OMS Community Edition checks whether the read and write permissions of the database user and the network connection to the database meet the requirements. You can start the data migration task only after all precheck tasks are completed. If an error is reported during the precheck:
