# Migrate data from a TiDB database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a TiDB database to OceanBase Database Community Edition.

## Background information

OMS Community Edition allows you to create a data migration task from a source TiDB database to a target OceanBase database. You can seamlessly migrate existing business data and incremental data from the source database to OceanBase database by using schema migration, full migration, and incremental synchronization.

TiDB supports hybrid transactional and analytical processing (HTAP) and is a hybrid distributed database. If you use a TiDB version earlier than V4.x, select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source. If you use TiDB V4.x or later, you can leave **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** unselected and directly synchronize incremental data from TiDB to OMS Community Edition.

If you select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source, you also need to deploy a TiCDC cluster and a Kafka cluster to synchronize incremental data from the TiDB database to OceanBase database. If the data migration task does not require incremental synchronization, you do not need to deploy a TiCDC cluster and a Kafka cluster.

![architecture8-zh](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oms/oms-enterprise/architecture8-zh.png)

TiCDC is an incremental data synchronization tool for TiDB. It achieves high availability by using a PD cluster (the scheduling module of the TiDB cluster, which usually consists of three PD nodes). TiKV Server is a TiKV node in the TiDB cluster. It actively sends change data to the TiCDC cluster in the form of change logs. The TiCDC tool obtains data from TiKV nodes through multiple TiCDC processes, processes the data, and then synchronizes the data to the Kafka cluster. The Kafka cluster stores incremental log information of the TiDB database that has been converted by the TiCDC tool. This way, OMS Community Edition can obtain the data from the Kafka cluster and synchronize the data to OceanBase database in real time during incremental data synchronization.

## Prerequisites

You have created database users for the source TiDB database and the target OceanBase database to migrate data and granted the required permissions to the users. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* The supported TiDB versions are V2.x, V3.x, V4.x, V5.x, V6.x, V7.x, and V8.x.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>Only TiDB Binlog is supported for TiDB V2.x and V3.x.</p>
   </main>

* If the target is a database, triggers cannot exist in the target. Otherwise, the data migration may fail.

* DDL synchronization is not supported when you migrate data from a TiDB database to OceanBase database.

* OMS Community Edition does not support migrating tables without primary keys or tables that contain spaces to OceanBase database.

* Data source identifiers and user accounts must be globally unique in OMS.

* OMS only supports migrating databases, tables, and column objects with ASCII-compliant names that do not contain special characters (|"'`()=;/& or line breaks).

* OMS Community Edition only supports TiCDC Open Protocol and does not support other protocols. If you use an unsupported protocol, an exception will be reported, such as a null pointer exception.

* Make sure that the enable-old-value = true parameter is added to the configuration for TiCDC to synchronize data to Kafka. Otherwise, the data synchronization message format may be abnormal. For more information, see [Description of the configuration file for a synchronization task](https://docs-archive.pingcap.com/zh/tidb/v4.0/manage-ticdc#%E5%90%8C%E6%AD%A5%E4%BB%BB%E5%8A%A1%E9%85%8D%E7%BD%AE%E6%96%87%E4%BB%B6%E6%8F%8F%E8%BF%B0).

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid impacting the operation of the data migration task.

* If the source database contains foreign keys with the same name, an error will be returned during schema migration. You can modify the foreign key constraint name and then resume the task.

* If the source database uses the UTF-8 character set, we recommend that you use a compatible character set for the destination database (such as UTF-8 or UTF-16) to avoid issues such as garbled characters in the destination database due to character set incompatibility.

   For more information about garbled characters in the Latin1 character set, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* In a reverse incremental migration task from a TiDB database to OceanBase Database Community Edition, if the version of OceanBase Database Community Edition is earlier than V3.2.x and the database contains a multi-partition table with a global unique index, updating the value of the partitioning key of the table may result in data loss during the migration.

* Do not write data to the topic used by TiCDC. Otherwise, the JDBC-connector will throw an exception and report a null pointer error.

* Make sure that the precision of columns such as DECIMAL, FLOAT, and DOUBLE in the destination database meets your expectations. If the precision of a destination column is smaller than that of the corresponding source column, data truncation may occur, which causes data inconsistency between the source and destination.

* If you change the unique index of the destination database, you must restart the incremental synchronization component. Otherwise, data may be inconsistent.

* If the clocks between nodes or between the client and the server are out of synchronization, the latency (incremental synchronization or reverse incremental migration) may be inaccurate.

   For example, if the clock is earlier than the standard time, the latency may be negative. If the clock is later than the standard time, the latency may be positive.

* In a schema migration task:

  * We recommend that you use import objects or matching rules to map the relationships between the source and destination databases.

  * We recommend that you manually create the schema in the destination database. If you use OMS to create the schema, skip some failed objects in the schema migration step.

* If the schemas of the source and destination databases are inconsistent, data may be inconsistent. Known scenarios are described as follows:

  * If you manually create the schema, the types of columns in the source and destination databases may be inconsistent due to implicit conversion that exceeds the support scope of OMS Community Edition.

  * If the length of a destination column is shorter than that of the corresponding source column, data may be truncated, which causes data inconsistency between the source and destination databases.

* When you use TiDB Database V2.x, V3.x, or V4.x, note the following points. For more information about TiDB Binlog, see [Overview](https://docs.pingcap.com/zh/tidb/stable/tidb-binlog-overview).

  * TiDB Binlog does not send heartbeats. Therefore, the incremental data point does not update when no data is updated in the source database.

  * Before incremental synchronization, the source database must have data updates. Otherwise, an error `data not existed` will be returned.

  * For tables without a primary key, other unique key (UK) information cannot be obtained from the incremental binlog. Therefore, all fields are treated as the primary key in the program. When updates are synchronized from the source to the destination, they are first deleted and then inserted.

  * Set `source.cdcDataFormat=tidbBinlog` in the Incr-Sync component to use the `tidbBinlog` data format.

* If you select only **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, make sure that the local incremental logs of the source database are retained for more than 48 hours.

   If you select **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, make sure that the local incremental logs of the source database are retained for at least seven days. Otherwise, the data migration task may fail or the data in the source and destination databases may be inconsistent because the incremental logs cannot be obtained.

         ```sql
         // parallel_servers_target specifies the number of parallel queries per server.
         // If you want to improve performance, we recommend that you set this parameter to a value greater than the number of physical CPU cores, such as 1.5 times the number of physical CPU cores. We recommend that you do not set this parameter to a value greater than 64 to avoid the kernel lock contention issue in OceanBase Database Community Edition.
         set global parallel_servers_target = 64;
         // data_copy_concurrency specifies the maximum number of concurrent data migration and replication tasks in the system.
         alter system set data_copy_concurrency = 200;
         ```
