# Migrate data from a TiDB database to OceanBase Database Community Edition

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a TiDB database to OceanBase Database Community Edition.

## Background information

OMS Community Edition allows you to create a data migration task from a source TiDB database to a destination OceanBase Database Community Edition instance. You can seamlessly migrate existing business data and incremental data from the source database to OceanBase Database Community Edition by using schema migration, full data migration, and incremental synchronization.

TiDB is a hybrid transactional/analytical processing (HTAP) database that supports online transaction processing (OLTP) and online analytical processing (OLAP). If you want to perform incremental synchronization, select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source.

If you select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source, you must deploy a TiCDC cluster and a Kafka cluster to perform incremental data synchronization from the TiDB database to OceanBase Database Community Edition. If incremental synchronization is not selected, you do not need to deploy a TiCDC cluster and a Kafka cluster.

![architecture8-zh](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oms/oms-enterprise/architecture8-zh.png)

TiCDC is an incremental data synchronization tool for TiDB. It ensures high availability by using a PD cluster, which consists of three PD nodes. TiKV Server is a TiKV node in the TiDB cluster. It actively sends change data to the TiCDC cluster in the form of change logs. The TiCDC tool obtains data from TiKV nodes through multiple TiCDC processes, processes the data, and synchronizes the data to the Kafka cluster. The Kafka cluster stores the incremental logs of the TiDB database converted by the TiCDC tool. This way, OMS Community Edition can obtain the corresponding data from the Kafka cluster and synchronize the data to OceanBase Database Community Edition in real time.

## Prerequisites

You have created a database user for the source TiDB database and the destination OceanBase Database Community Edition instance and granted the required permissions to the user. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* The supported versions of TiDB are V2.x, V3.x, V4.x, V5.x, V6.x, V7.x, and V8.x. The supported versions of Kafka are V0.9, V1.0, V2.x, V3.x, and V4.x.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>Only TiDB Binlog is supported for TiDB databases of V2.x and V3.x. </p>
   </main>

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If a trigger exists in the destination, the data migration task may fail.

* DDL operations cannot be synchronized when you migrate data from a TiDB database to OceanBase Database Community Edition.

* Tables without a primary key cannot be synchronized from a TiDB database to OceanBase Database Community Edition.

* Data source identifiers and user accounts must be globally unique in OMS.

* OMS Community Edition supports only databases, tables, and columns whose names contain only ASCII characters and do not include special characters (spaces, line breaks, or |"'`()=;/&).

* OMS Community Edition supports only the TiCDC Open Protocol. If you use another protocol, an exception will be thrown when the JDBC-Connector is used. The error message will be a null pointer error.

* Make sure that the `enable-old-value=true` parameter is added to the TiCDC configuration when you synchronize data to Kafka. Otherwise, the data synchronization message format may be abnormal. For more information, see [Description of the synchronization task configuration file](https://docs-archive.pingcap.com/zh/tidb/v4.0/manage-ticdc#%E5%90%8C%E6%AD%A5%E4%BB%BB%E5%8A%A1%E9%85%8D%E7%BD%AE%E6%96%87%E4%BB%B6%E6%8F%8F%E8%BF%B0).

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid affecting the running of the data migration task.

* If the source database contains foreign keys with the same name, an error will be returned during schema migration. You can modify the names of the foreign key constraints and then resume the task.

* If the character set of the source database is UTF-8, we recommend that you use a character set compatible with the source character set (such as UTF-8 or UTF-16) for the destination database to avoid garbled characters in the destination database.

   For more information about garbled characters in the Latin1 character set, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* When you perform reverse incremental synchronization from a TiDB database to OceanBase Database Community Edition, if the destination database is of a version earlier than V3.2.x and contains a multi-partition table with a global unique index, updating the values of the partitioning key of the table may cause data loss during data migration.

* Do not write data to the topic used for TiCDC synchronization. Otherwise, an exception will be returned and a null pointer error will be reported.

* Make sure that the precision of the DECIMAL, FLOAT, or DOUBLE column types is migrated as expected in OceanBase Database Community Edition. If the precision of the destination column type is less than that of the source column type, truncation may occur, which will cause data inconsistency between the source and destination.

* If you change the unique index of the destination database, you must restart the incremental synchronization component. Otherwise, data inconsistency may occur.

* If the clocks of the nodes are out of sync, or the clocks of the client terminal and server are out of sync, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be inaccurate.

* In the scenario of schema migration:

  * We recommend that you use an import object or matching rule to map the relationships between the source and destination databases.

  * We recommend that you create the table schema in the destination database. If you use OMS to create the table schema, skip the failed objects in the schema migration step.

* If the schemas of the source and destination databases are not completely consistent, data inconsistency may occur. The following scenarios are known to cause data inconsistency:

  * When you manually create a table schema that is out of the supported scope of OMS Community Edition, implicit conversion may occur, which will cause the column types of the source and destination databases to be inconsistent.

  * If the length of the destination data is less than that of the source data, data truncation may occur, which will cause data inconsistency between the source and destination databases.

* When you use TiDB Database V2.x, V3.x, or V4.x, note the following issues. For more information about TiDB Binlog, see [TiDB Binlog](https://docs.pingcap.com/zh/tidb/stable/tidb-binlog-overview).

  * TiDB Binlog does not support heartbeat packets. If no updates are performed in the source database, the incremental data position will not be updated.

  * Before you start incremental synchronization, the source database must have updates. Otherwise, an error `data not existed` will be returned.

  * For tables without a primary key, the incremental Binlog cannot obtain information about other unique keys. In this case, all fields will be treated as the primary key. When an update operation is synchronized from the source to the destination, the update will be first deleted and then inserted.

  * If you set `source.cdcDataFormat=tidbBinlog` for the Incr-Sync component, you can use the `tidbBinlog` data format.

* When you create a data migration task and configure only **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>**, the data migration task requires that the local incremental logs of the source database be retained for more than 48 hours.

   If you create a data migration task and configure **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>**, the data migration task requires that the local incremental logs of the source database be retained for at least 7 days. Otherwise, the data migration task may fail because the incremental logs cannot be obtained, or data inconsistency may occur between the source and destination databases.

        * Modify the sys tenant parameters

            ```sql
            // parallel_servers_target specifies the parallel query queuing condition for each server.
            // For optimal performance, we recommend that you set this parameter to a value greater than the number of physical CPU cores, such as 1.5 times the number of physical CPU cores. The value must not exceed 64 to avoid lock contention in the OceanBase Database Community Edition kernel.

            ```

            ```sql
            // _temporary_file_io_area_size specifies the limit on the file memory buffer.
            alter system set _temporary_file_io_area_size = '10' tenant = 'xxx';

            alter system set sys_bkgd_net_percentage = 100;
            ```

         ```sql
         // parallel_servers_target specifies the parallel query queuing condition for each server.
         ```

   In the **<UI-TERM key="oms-community.Sync.New.Precheck">Precheck</UI-TERM>** phase, OMS Community Edition checks whether the read and write permissions of the database user and the network connection of the database meet the requirements. You can start a data migration task only after all precheck tasks are passed. If an error occurs during the precheck:

   * You can troubleshoot and fix the error, and then perform the precheck again until it succeeds.

   * You can also click **<UI-TERM key="must.AlertTips.commponents.ErrorDetail.Skip">Skip</UI-TERM>** in the Actions column of the error item.
