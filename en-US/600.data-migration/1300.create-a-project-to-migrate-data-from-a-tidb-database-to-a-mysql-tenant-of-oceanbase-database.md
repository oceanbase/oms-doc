# Migrate data from a TiDB database to OceanBase Database

This topic describes how to use OceanBase Migration Service (OMS) Community Edition to migrate data from a TiDB database to OceanBase Database.

## Background information

OMS Community Edition allows you to migrate data from a source TiDB database to a destination OceanBase Community Edition database. You can seamlessly migrate existing business data and incremental data from the source database to OceanBase Community Edition through schema migration, full data migration, and incremental synchronization.

TiDB is a hybrid transactional and analytical processing (HTAP) database that supports online transaction processing and online analytical processing. If you are using a TiDB database of a version earlier than V4.x, you must select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source. If you are using a TiDB database of V4.x or later, you can skip this step and directly use OMS Community Edition to synchronize incremental data from the TiDB database.

If you select **<UI-TERM key="oms-community.endpoints.TIDBForm.BindKafkaDataSource">Bind Kafka Data Source</UI-TERM>** when you create a TiDB data source, you must deploy a TiCDC cluster and a Kafka cluster to synchronize incremental data from the TiDB database to OceanBase Community Edition. If you do not select this option, you do not need to deploy a TiCDC cluster and a Kafka cluster.

![architecture8-zh](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oms/oms-enterprise/architecture8-zh.png)

TiCDC is an incremental data synchronization tool for the TiDB database. It achieves high availability by using a PD cluster, which consists of three PD nodes and serves as the scheduling module of the TiDB cluster. TiKV Server is a TiKV node in the TiDB cluster. It actively sends change data to the TiCDC cluster in the form of change logs. The TiCDC tool obtains data from multiple TiCDC processes, processes the data, and synchronizes the data to the Kafka cluster. The Kafka cluster stores incremental logs of the TiDB database converted by the TiCDC tool, so that OMS Community Edition can obtain the data from the Kafka cluster and synchronize the data to OceanBase Community Edition in real time.

## Prerequisites

A database user is created for the source TiDB database and the destination OceanBase Community Edition database, and the user is granted the required permissions. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* The supported TiDB database versions are V2.x, V3.x, V4.x, V5.x, V6.x, V7.x, and V8.x. The supported Kafka versions are V0.9, V1.0, V2.x, V3.x, and V4.x.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>TiDB databases of versions V2.x and V3.x support only TiDB Binlog. </p>
   </main>

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If a trigger exists, the data migration may fail.

* DDL operations cannot be synchronized when you migrate data from a TiDB database to OceanBase Community Edition.

* Tables without a primary key cannot be synchronized when you synchronize incremental data from a TiDB database to OceanBase Community Edition.

* Data source identifiers and user accounts must be globally unique in the OMS system.

* OMS Community Edition supports only objects whose database names, table names, and column names contain only ASCII characters and do not contain special characters (spaces, line breaks, or |"'`()=;/&).

* OMS Community Edition supports only the TiCDC Open Protocol. If you use another protocol, an error of null pointer exception is returned when the JDBC-Connector is started.

* Make sure that the `enable-old-value=true` parameter is added to the TiCDC configuration for synchronization to Kafka. Otherwise, an error may occur during data synchronization. For more information, see [Description of synchronization task configuration files](https://docs-archive.pingcap.com/zh/tidb/v4.0/manage-ticdc#%E5%90%8C%E6%AD%A5%E4%BB%BB%E5%8A%A1%E9%85%8D%E7%BD%AE%E6%96%87%E4%BB%B6%E6%8F%8F%E8%BF%B0).

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid affecting the running of the data migration task.

* If the source database contains foreign keys with the same name, an error is returned during schema migration. You can modify the names of the foreign key constraints and then resume the task.

* If the source database uses the UTF-8 character set, we recommend that you use a character set that is compatible with the source character set (such as UTF-8 or UTF-16) for the destination database. Otherwise, garbled characters may appear in the destination database.

   For more information about garbled characters in the Latin1 character set, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md).

* During reverse incremental migration from a TiDB database to OceanBase Database Community Edition, if OceanBase Database Community Edition is earlier than V3.2.x and contains a multi-partition table with a global unique index, updating the values of the partitioning key of the table may result in data loss during data migration.

* Do not write data to the topic used for synchronization with TiCDC. Otherwise, an exception is returned, and a null pointer error is reported.

* Verify whether the precision of the DECIMAL, FLOAT, or DOUBLE column types is migrated correctly in OceanBase Database Community Edition. If the precision of the destination column type is less than that of the source column type, truncation may occur, resulting in data inconsistency between the source and destination databases.

* If you change the unique index of the destination database, you must restart the incremental synchronization component. Otherwise, data inconsistency may occur.

* If the clocks of the nodes are out of sync, or the clocks of the client terminal and server are out of sync, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be positive.

* In the scenario of table aggregation:

  * We recommend that you map the relationships between the source and destination databases by using an import object or a matching rule.

  * We recommend that you create the table structure in the destination database. If you use OMS to create the table structure, skip failed objects in the schema migration step.

* If the table structures of the source and destination databases are not exactly the same, data inconsistency may occur. The following are known scenarios:

  * If you manually create a table structure that is out of the supported scope of OMS Community Edition, implicit conversion may occur, resulting in type inconsistency between columns of the source and destination databases.

  * If the length of the destination data is less than that of the source data, data truncation may occur, resulting in data inconsistency between the source and destination databases.

* When you use TiDB Database V2.x, V3.x, or V4.x, note the following issues. For more information about TiDB Binlog, see [TiDB Binlog](https://docs.pingcap.com/zh/tidb/stable/tidb-binlog-overview).

  * TiDB Binlog does not support heartbeat packets. If no data is updated in the source database, the incremental data point will not be updated.

  * Before you start incremental synchronization, the source database must have been updated. Otherwise, an error `data not existed` is returned.

  * For tables without a primary key, the incremental Binlog cannot obtain information about other unique keys. In this case, all fields are treated as primary keys. When an update operation is synchronized from the source database to the destination database, the update operation is first deleted and then inserted.

  * If you set `source.cdcDataFormat=tidbBinlog` for the Incr-Sync component, you can use the `tidbBinlog` data format.

* If you configure only **<UI-TERM key="oms-community.SyncParameter.components.IncrSyncForm.IncrementalSynchronization">Incremental Synchronization</UI-TERM>** when you create a data migration task, the data migration task requires that the local incremental logs of the source database are retained for more than 48 hours.

   If you configure **<UI-TERM key="oms-community.Operation.constants.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the data migration task requires that the local incremental logs of the source database are retained for at least 7 days. Otherwise, the data migration task may fail because the incremental logs cannot be obtained. In addition, data inconsistency may occur between the source and destination databases.

            ```sql
            // parallel_servers_target specifies the parallel query queuing condition for each server.
            // For performance optimization, we recommend that you set this parameter to a value greater than the number of physical CPUs, such as 1.5 times the number of physical CPUs. However, the value must not exceed 64 to avoid lock contention in the OceanBase Database Community Edition kernel.
            set global parallel_servers_target = 64;
            ```

        * Adjust the business tenant parameters.

            ```sql
            // _temporary_file_io_area_size specifies the limit on the memory buffer for files.
            alter system set _temporary_file_io_area_size = '10' tenant = 'xxx';
            // sys_bkgd_net_percentage specifies the percentage of background network traffic for 4.x versions.
            alter system set sys_bkgd_net_percentage = 100;
            ```

      * If you are using OceanBase Database Community Edition V3.x, use a command-line client to adjust the following sys tenant parameters.

         ```sql
         // parallel_servers_target specifies the parallel query queuing condition for each server.
         // For performance optimization, we recommend that you set this parameter to a value greater than the number of physical CPUs, such as 1.5 times the number of physical CPUs. However, the value must not exceed 64 to avoid lock contention in the OceanBase Database Community Edition kernel.
         set global parallel_servers_target = 64;
         // data_copy_concurrency specifies the maximum number of concurrent data migration and replication tasks that can be executed in the system.
         alter system set data_copy_concurrency = 200;
         ```

You can start a data migration task only after all precheck tasks are completed. If an error occurs during the precheck:
