# Data migration in a disaster recovery and active-active scenario

OceanBase Migration Service (OMS) Community Edition supports data migration between OceanBase Database Community Edition, MySQL databases, and OceanBase Database Community Edition in a disaster recovery and active-active scenario.

## Background information

As more users use OMS Community Edition for data migration, the scenarios it needs to address are becoming increasingly diverse. In addition to the widely used single-region data migration and synchronization scenarios, OMS Community Edition also supports data migration between multiple regions and data synchronization or active-active synchronization between remote cities.

Currently, [MySQL Database to OceanBase Database Community Edition](../600.data-migration/200.create-a-project-to-migrate-data-from-a-mysql-database-to-a-mysql-tenant-of-oceanbase-database.md) and [OceanBase Database Community Edition](../600.data-migration/1100.migrate-data-within-oceanbase-database.md) data migration tasks support disaster recovery and active-active scenarios. The disaster recovery and active-active scenarios supported by OMS Community Edition are as follows:

* Data migration and synchronization within the same city

* Active-standby disaster recovery within the same city

* Active-active within the same city

* Data migration and synchronization between remote cities

* Active-standby disaster recovery between remote cities

* Active-active between remote cities

Active-standby disaster recovery is commonly used in scenarios where data disaster recovery is required. Using OMS Community Edition, you can create a data synchronization task from the primary IDC to the standby IDC to ensure real-time synchronization. In the event of a disaster or outage at the primary IDC, the business can switch to the standby IDC to avoid any impact on operations.

However, active-standby disaster recovery can lead to underutilization and waste of resources at the standby IDC. To address this, OMS Community Edition provides an active-active solution, where both IDCs handle actual business traffic. In an active-active scenario, two databases, A and B, are used. The application writes data to both databases according to specific rules, ensuring that all application data is retained in both databases. In a non-active-active scenario, data is written to database A and not to database B. Similarly, data written to database B is not written to database A.

## Prerequisites

* You have created the corresponding schema in the destination OceanBase Database Community Edition instance. OMS Community Edition supports migrating tables and columns, so you need to create the corresponding schema in the destination instance in advance.

* You have created dedicated database users for data migration tasks in both the source and destination OceanBase Database Community Edition instances and granted the necessary privileges to these users. For more information, see [Create a database user](../800.create-and-manage-data-sources/300.create-a-database-user.md).

## Limitations

* **Limitations on operations on the source database**

   **Do not perform DDL operations to modify the schema of a database or table during schema migration or full data migration. Otherwise, the data migration task may be interrupted.**

* Disaster recovery and active-active tasks between OceanBase Database Community Edition instances only support migrating tables with unique keys.

* During disaster recovery and active-active data migration tasks, you cannot add or remove objects while the task is running.

* In incremental synchronization and reverse incremental scenarios, you cannot select **<UI-TERM key="oms-community.components.MigrationParamsConfig.MigrationParamsDetail.SchemaChangeDdl">DDL Synchronization</UI-TERM>**.

* If the destination is a database, OMS Community Edition does not support triggers in the destination. If triggers exist, the data migration may fail.

* In incremental synchronization scenarios, if `useTargetIndex = false` and the destination database uses the BINARY type for the primary or unique key, and the length of the migrated data from the source does not match the length of the BINARY type field in the destination, the UPDATE or DELETE operations may not match the data, leading to data quality risks.

* Data source identifiers and user accounts must be globally unique within the OMS Community Edition system.

* OMS Community Edition only supports migrating databases, tables, and columns with ASCII-compliant names that do not contain special characters (including line breaks, spaces, and |"'`()=;/&).

* In OceanBase Database Community Edition versions earlier than V4.0.0, the presence of temporary tables can cause full data migration to fail.

* OMS Community Edition does not support using OceanBase standby databases as the source.

## Considerations

* We recommend that you migrate no more than 1,000 tables at a time to avoid affecting the running of data migration tasks.

* For OceanBase Database Community Edition V4.x, we recommend that you enable log archiving. After log archiving is enabled, if a Clog is reclaimed, OMS can still achieve incremental synchronization by consuming the archived logs. For more information about how to enable log archiving, see [Log archiving](https://www.oceanbase.com/docs/community-observer-cn-10000000000901781).

* If the character set of the source database is UTF-8, we recommend that you use a compatible character set (such as UTF-8 or UTF-16) for the destination database to avoid garbled characters in the destination database.

   If the character set of the source database is Latin1, see [Garbled characters in the Latin1 character set](../1400.faq/500.data-migration-1/400.full-migration/400.latin1-character-set-garbled.md) for more information.

* If the clocks of the nodes or between the client and server are not synchronized, the delay (incremental synchronization or reverse incremental) may be inaccurate.

   For example, if the clock is earlier than the standard time, the delay may be negative. If the clock is later than the standard time, the delay may be inaccurate.

* In disaster recovery or active-active tasks from OceanBase Database Community Edition to a MySQL database or OceanBase Database Community Edition, if the source database is OceanBase Database Community Edition of a version earlier than V3.2.x and contains a multi-partition table with a global unique index, data may be lost during migration if you update the value of the partitioning key.

* Confirm whether the migration precision of the DECIMAL, FLOAT, or DOUBLE column types meets your expectations in OceanBase Database Community Edition. If the precision of the destination column type is less than that of the source column type, data truncation may occur, resulting in data inconsistency between the source and destination.

* If you change the unique index of the destination database without enabling DDL synchronization, you must restart the incremental synchronization component to avoid data inconsistency.

* In the scenario of table aggregation:

  * We recommend that you use an import object or matching rule to map the relationships between the source and destination databases.

  * We recommend that you create the table structure in the destination database. If you use OMS Community Edition to create the table structure, skip failed objects in the schema migration step.

* In a data migration task from OceanBase Database Community Edition to OceanBase Database Community Edition where DDL synchronization is enabled, if the source database table is renamed (RENAME), we recommend that you restart the task to avoid data loss during incremental synchronization.

* When you migrate data from OceanBase Database Community Edition to OceanBase Database Community Edition, the destination database objects are created in lowercase by default based on the `lower_case_table_names = 1` parameter.

* If the table structures of the source and destination databases are not completely consistent, data inconsistency may occur. The following are known scenarios:

  * If you manually create a table structure that exceeds the supported scope of OMS Community Edition, implicit conversion may occur, resulting in type inconsistency between columns of the source and destination databases.

  * If the data length of the destination database is shorter than that of the source database, data truncation may occur, resulting in data inconsistency between the source and destination databases.

* If you only enable **<UI-TERM key="oms-community.New.components.MigrationObjectForm.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for more than 48 hours.

   If you enable **<UI-TERM key="oms-community.New.components.MigrationObjectForm.FullMigration">Full Migration</UI-TERM>** + **<UI-TERM key="oms-community.Migration.constants.IncrementalMigration">Incremental Synchronization</UI-TERM>** when you create a data migration task, the local incremental logs of the source database must be retained for at least 7 days. Otherwise, the data migration task may fail because the incremental logs cannot be obtained, or data inconsistency may occur between the source and destination databases.

* If the value of the `binlog_row_image` parameter is not `FULL` when the application is started, OceanBase Database Community Edition sets it to `FULL`. In this case, you must restart the application. Otherwise, OceanBase Database Community Edition will miss log information, which will cause data synchronization issues in OMS Community Edition. The following command is used to set the parameter:

   ```shell
   set global binlog_row_image = 'FULL';
   ```

      |Target Object Existence Handling Strategy| The value can be **<UI-TERM key="must.PreCheck.constants.Skip">Ignore</UI-TERM>** or **<UI-TERM key="oms-community.New.components.ParameterForm.StopProject">Stop Migration</UI-TERM>**:<ul><li> If you select **<UI-TERM key="oms-community.New.components.ParameterForm.Ignore">Ignore</UI-TERM>**, OMS Community Edition will log conflicting data and retain the original data when the target table contains data that conflicts with the data to be written. <main id="notice" type='notice'><h4>Notice</h4><p>When you select <b>Ignore</b>, full validation will pull data in IN mode.       If you allow index post-creation, we recommend that you adjust the parameters based on the hardware conditions of OceanBase Database Community Edition and the current business traffic.

      * If you are using OceanBase Database Community Edition V4.x, use the black-screen client to adjust the following sys tenant parameters and business tenant parameters.

        * Adjust the sys tenant parameters

            ```sql
            // parallel_servers_target specifies the parallel query queuing conditions on each server.
            // For better performance, we recommend that you set this parameter to a value greater than the number of physical CPUs, such as 1.5 times the number of physical CPUs. However, the value should not exceed 64 to avoid lock contention issues in the OceanBase Database Community Edition kernel.
            set global parallel_servers_target = 64;
            ```

        * Adjust the business tenant parameters

            ```sql
            // File memory buffer limit
            alter system set _temporary_file_io_area_size = '10' tenant = 'xxx';
            // Disable throttling in 4.x
            alter system set sys_bkgd_net_percentage = 100;
            ```

      * If you are using OceanBase Database Community Edition V3.x, use the black-screen client to adjust the following sys tenant parameters.

         ```sql
         // parallel_servers_target defines the conditions for queuing queries in parallel on each server.
         // For performance improvement, we recommend that you set the value of this parameter to be greater than the number of physical CPUs, for example, 1.5 times as many. The value cannot exceed 64. Otherwise, it may cause a kernel resource contention issue in OceanBase Database Community Edition.
         set global parallel_servers_target = 64;
         // data_copy_concurrency sets the maximum number of data migration and replication tasks that can be executed in parallel in the system.
         alter system set data_copy_concurrency = 200;
         ```

8. Click **<UI-TERM key="oms-community.Migration.New.Precheck">Precheck</UI-TERM>**. The system performs a precheck on the data migration task.

   In the **<UI-TERM key="oms-community.Sync.New.Precheck">Precheck</UI-TERM>** step, OMS Community Edition checks whether the read and write permissions of the database user and the network connection of the database meet the requirements.
