# Performance troubleshooting and optimization for data synchronization from OceanBase Database Community Edition to Kafka

## Performance troubleshooting procedure

1. Use the following methods to determine whether the Store component has bottlenecks.


2. After the Store component is ruled out as the cause, check the performance-related parameter configurations of Full-Import/Incr-Sync.

## Performance-related configurations for Full-Import/Incr-Sync components

Usually, you only need to set useSchemaCache to true in the Source to meet the performance requirements in most scenarios. If the RPS still cannot meet the requirements, you can set buildRecordConcurrent to true.

### Source

| Parameter  |    Description  |
|-------------|----------------|
| useSchemaCache | Specifies whether to cache the schema when the store component reads data. Valid values: true and false. Default value: false.<br> If set to `true`, the store component caches the schema when reading data, which accelerates the message conversion of the store component. |
| buildRecordConcurrent | Specifies whether to asynchronously convert store messages. Valid values: true and false.<br> If set to true, data is pulled from the store component and converted into messages in parallel. The number of worker threads is the same as the value of workerNum. |

### Sink

The following two parameters specify the properties of the Kafka producer client.

| OMS Community Edition parameter | Corresponding Kafka client parameter | Description |
|-------------|------------------------|---------------|
| lingerMs  | ProducerConfig.LINGER_MS_CONFIG | The waiting time for sending batches of data in Kafka. If you want to improve the throughput, you can increase the number of data records sent in each batch. Default value: 10, in milliseconds. |
| batchSize | ProducerConfig.BATCH_SIZE_CONFIG | The maximum number of messages that can be sent in each batch by the Kafka client. Default value: 1048576, in bytes (1 MB). |
| workerNum |     | The number of concurrent worker threads of the sink. Default value: 16. |

When enablePreprocessConfig is set to true in the coordinator, lingerMs and batchSize will be automatically configured based on the JVM memory. If you manually specify these two parameters, your settings will take precedence.

```shell
# View the automatically configured parameters.
grep "auto set " connector.log
# View the parameters actually used by the program.
cat conf/runningConf.json
```

### Coordinator

Shuffle-related configurations of OMS Community Edition

| Parameter  |    Description     |
|-----------------|--------------------|
| shuffleBucketSize   | The number of buckets. OMS Community Edition usually reads a batch of data from a bucket and sends the data, and then reads and sends the next batch of data from the bucket. The number of buckets determined the number of records that can be sent at the same time. Default value: 128. |
| shuffleFlushIntervalMs | The time interval for scheduling the read of data from a bucket. The smaller the interval, the more real-time the data. Unit: milliseconds. Default value: 100. |
| shuffleMinBatchSize | The number of records in a bucket must be greater than or equal to the value of shuffleMinBatchSize for the data in the bucket to be read and sent. If the number of records in the bucket is less than shuffleMinBatchSize, the data in the bucket is read and sent after shuffleFlushIntervalMs. Default value: 20. |
| shuffleMaxBatchSize | The maximum number of records that can be read from a bucket at a time. Default value: 64. |

## Use Arthas for performance analysis

```SQL
# Log in to the OMS Community Edition container.
cp /root/arthas-bin.zip /home/ds
su - ds
unzip arthas-bin.zip

/opt/alibaba/java/bin/java -jar arthas-boot.jar pid(Incremental component process number)
profiler start
profiler getSamples
profiler status
# After waiting for 1 minute, enter the stop command. The flame graph is output to an HTML file.
profiler stop --format html
# Exit Arthas.
exit
```
