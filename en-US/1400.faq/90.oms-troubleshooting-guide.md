## Issues during installation

Log in to the OMS Community Edition container and check whether the OMS Community Edition components are working properly. If any component is not working properly, check the corresponding logs.

```shell
supervisorctl status 
```

During installation, the following issues may occur:

* The port is occupied.

* The permissions of the metadata database provided for OMS Community Edition are incorrect.

* The Docker environment of some operating systems is faulty, resulting in file permission issues and preventing the service from starting. In this case, install OMS Community Edition on a different system.

* The user system uses cgroup2, causing the OMS Community Edition machine to be in an abnormal state. OMS V4.2.4 and later versions resolve this issue.

### Concurrency, JVM memory, and number of records per shard

This section addresses most performance issues.

| Issue type |  Solution |
|----------|--------------|
|Concurrency | The source concurrency is specified by `source.workerNum`, and the sink concurrency is specified by `sink.workerNum`. Typically, the source and sink concurrency settings are the same during full migration. For incremental synchronization, you do not need to set the sink concurrency. <br>The concurrency is related to the number of CPU cores. The maximum value can be set to CPU*4. At the same time, you need to check whether other migration tasks are running on the machine. |
|JVM memory | `coordinator.connectorJvmParam`. The main parameters to adjust are `-Xms8g` (initial memory), `-Xmx8g` (maximum memory), and `-Xmn4g` (additional memory). The adjustment rules are as follows: <ul><li>Initial memory = maximum memory </li><li>Additional memory = maximum memory - 4GB</li><li>Typically, each concurrency corresponds to 1GB of memory. For example, 32 concurrent tasks require a maximum memory of 32GB.</li></ul> |
|Number of records per shard | `source.sliceBatchSize`, default value is 600.<br>For large tables, 10000 is usually sufficient. If you set it too high, it will consume a lot of memory. You can decide whether to modify it based on the `slice_queue` in the `logs/msg/metrics.log` file. If it is 0, you need to increase the number of records per shard. This is because the Source Worker thread will pull shards from `slice_queue`. If `slice_queue` is 0, it means there are no shards, and the Source Worker thread will wait idly.|

Index creation is usually required after full migration to improve the efficiency of full migration. If the destination database is OceanBase Database, you can configure the concurrency of index creation by setting the `ob.parallel` parameter in the `struct.transfer.config` system parameter.

### Incremental synchronization

Transaction sharding: `source.splitThreshold`. If incremental delay occurs due to batch operations at the source, you can adjust this parameter. The default value is 128. For batch operations of type `INSERT`, a larger value is better, with a maximum of 512. For batch operations of type `UPDATE` and `DELETE`, a smaller value is better, with a minimum of 1.

### metrics.log analysis

#### Determine where the bottleneck is

Slice sharding -> source reads from the source -> dispatcher distributes data -> sink writes to the destination

* If `slice_queue` is greater than 0, the bottleneck is not here. If `slice_queue` is 0, the shards are slow. You can increase `source.sliceBatchSize` to increase the number of records per shard. In multi-table scenarios, you can also increase `source.sliceWorkerNum` to increase the number of shard worker threads.

* If `source_worker_num` is less than `source_worker_num_all`, the bottleneck is not in the source reading.

* If `sink_worker_num` is less than `sink_worker_num_all`, the bottleneck is not in the sink writing.

* If `dispatcher.ready_execute_batch_size` is 0, there is no bottleneck in writing. If `ready_execute_batch_size` is greater than 0, writing is slow.

* If `dispatcher.wait_dispatch_record_size` is 0, there is no bottleneck in distribution. If `wait_dispatch_record_size` is greater than 0, there is a bottleneck in the internal calculation of data partitioning in OMS (partitioning is usually delayed and calculation is time-consuming). In bypass scenarios, you can disable partitioning calculation by setting `sink.enablePartitionBucket=false`. There may also be hot data. For more information, see the [Hotspot issue](https://www.oceanbase.com/knowledge-base/oms-ee-1000000000253328) section.

* If the JVM memory is insufficient, full GC may occur, significantly reducing efficiency and causing database disconnection errors that are easy to misinterpret. You can log in to the OMS Community Edition container to view the GC status of the process.

## Typical use cases and features

### Multi-table aggregation

When you migrate data from multiple tables in a source database to a single table or partitioned table in the destination database, you can use the following example:

```SQL
-- Source tables, primary key ID, and unique key (UK) field uk_id
CREATE TABLE test_01(id bigint not null AUTO_INCREMENT,uk_id bigint not null,...);
CREATE TABLE test_02(id bigint not null AUTO_INCREMENT,uk_id bigint not null,...);

-- Destination table
CREATE TABLE test(id_new bigint not null AUTO_INCREMENT,uk_id bigint not null,...,
                 PRIMARY KEY (id_new,uk_id),
                 unique key(uk_id))
PARTITION BY HASH(uk_id)
PARTITIONS 4
;
```

Common issues include:

* When you create a data migration task, the source tables are renamed in batches.

  * Use **<UI-TERM key="oms-community.New.components.MigrationObjectForm.MatchRules">Match Rules</UI-TERM>** to configure the renaming.

  * Use the configuration `src_schema.test_*=dst_schema.test`.

* The ID field in the source tables is an auto-increment field and is duplicated. The destination table uses a new field name as the auto-increment primary key.

  * The ID field in the source tables does not need to be migrated to the destination table. The `id_new` field in the destination table is a new auto-increment column.

  * When you perform a full migration, set the parameter `sink.ignoreRedunantColumnsReplicate=true`. The ID field will be ignored during the full migration.

  * When you perform an incremental synchronization, set `sink.ignoreRedunantColumnsReplicate=true` to ignore the ID field.

* The destination table is a partitioned table. In OceanBase Database, the primary key (PK) field must include the partitioning field. How can you verify the data?

  * When you perform a full verification, set `task.sourceMasterSection.matchAllColumn=false`. The ID field in the source table will not be involved in the verification. In this case, the source table must have a non-nullable unique key (UK). Otherwise, the verification cannot be performed.

  * When you perform a full verification, set the `inmod` mode: `filter.verify.inmod.tables=.*;.*;.*`. For more information, see [Full-Verification component parameters](../900.o-m-manual/400.components/500.component-parameters/800.full-verification-parameters.md).

### Migration of tables without a primary key in OceanBase Database

When OceanBase Database is the source database, OMS Community Edition uses the hidden column `__pk_increment` as the primary key for tables without an intermediate table. During schema migration, the destination table will have an additional column named `OMS_PK_INCRMT`.

* If you have performed a forward switch, the `OMS_PK_INCRMT` column will eventually be deleted.

* If you have not performed a forward switch and the destination database is used as the source database for the next task, an exception will occur. In this case, you must manually delete the `OMS_PK_INCRMT` column to avoid the exception.

### Direct load

In addition to the commonly used concurrency parameter, you can also set the `sink.serverParallel` parameter to specify the number of server-side threads for direct load tasks. The default value is 8. This parameter affects the number of worker threads and the concurrency of OceanBase Database for direct load tasks.

### Reverse incremental migration

If you want to roll back data or use the original database as a standby database, we recommend that you enable **<UI-TERM key="oms-community.Migration.constants.ReverseIncrement">Reverse Increment</UI-TERM>** when you create a data migration task. If MySQL is the source database (for example, MySQL to OceanBase Database), you must manually create the transaction database `omstxndb` in MySQL. If you do not create this transaction database, an exception will be thrown indicating that the `omstxndb` database does not exist.

### Disaster recovery with dual-active deployment

If your application requires dual writes or gray-scale switching, you can use the disaster recovery with dual-active deployment feature of OMS Community Edition. This feature supports dual-active deployment between MySQL and OceanBase Database, and between OceanBase Databases. OMS Community Edition automatically sets the parameters to prevent cyclic replication. Note that all tables must have a primary key (PK) or a unique key (UK) in a dual-active deployment.

1. You have two databases, A and B.

2. Your application writes data to A and B according to specific rules.

    In a non-dual-write scenario, data written to A will not be written to B, and data written to B will not be written to A.

3. You need to retain all data written to A and B.

### Full verification

Full verification can be performed in two modes:

* Default mode: Both the source and destination databases use range queries on shards.

* Inmod mode: The source database uses range queries on shards, and the destination database queries the destination data using the primary key (PK) or unique key (UK) obtained from the source data. The `filter.verify.inmod.tables` parameter specifies the tables to be verified in this mode.

  Here are some examples:

  * To verify all tables in the current task using the inmod mode: `filter.verify.inmod.tables=.*;.*;.*`

  * To verify the T1 table in the D1 database using the inmod mode: `filter.verify.inmod.tables=D1;T1;.*`

  * To verify the T1 and T2 tables in the D1 database using the inmod mode: `filter.verify.inmod.tables=D1;T1;.*|D1;T2;.*`

  * To verify the T1 and T2 tables in the D1 database and the T3 and T4 tables in the D2 database using the inmod mode: `filter.verify.inmod.tables=D1;T1;.*|D1;T2;.*|D2;T3;.*|D2;T4;.*`
