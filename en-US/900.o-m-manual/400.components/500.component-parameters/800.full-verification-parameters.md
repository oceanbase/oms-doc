# Full-Verification component parameters

| Parameter | Default value | Description | Supported version |
|-------------|-----------|---------------|-------------|
| limitator.platform.threads.number |  The default value and the full verification resource configuration are related. | The number of read threads for data sources. The number of read threads for the source and target ends depends on the parameters `limitator.platform.threads.number` and `limitator.source.max.thread.size`. The calculation logic is as follows:<ol><li>The default value of the `limitator.source.max.thread.size` parameter is 6.</li><li>The initial value of the read threads on one end is `limitator.platform.threads.number`/2. </li><li>The number of read threads is the smaller value between `limitator.source.max.thread.size` and the initial value of the read threads on one end.</li></ol>For example, if `limitator.platform.threads.number`=10, then the source and target ends each have 5 read threads. If `limitator.platform.threads.number`=14, then the source and target ends each have 6 read threads. | All versions |
| limitator.platform.split.threads.number | 16 | The number of split threads for verification. | All versions |
| limitator.select.batch.max  | 600 | The maximum number of records in each split. When the split is based on the primary key (PK) or unique key (UK), this value represents the maximum number of records processed in each split.<main id="notice" type='explain'><h4>Note</h4><p>Do not modify this parameter unless it is the performance bottleneck of the verification. </p></main>| All versions |
| limitator.reviewer.rounds.max | 20  | The number of recheck rounds.<main id="notice" type='explain'><h4>Note</h4><p>If data inconsistencies exist and you need to quickly obtain the inconsistent results or have confirmed that the data is inconsistent, you can set this parameter to 0 to skip the recheck and directly output the data comparison results. </p></main>| All versions |
| limitator.reviewer.review.batch.max |  100 | The number of unique keys to be verified in each recheck task. | All versions |
| limitator.review.query.batch.limit |100  | 【Recheck】The number of unique keys to be queried from the source or target end in each query. This parameter works with `limitator.reviewer.review.batch.max`. For example, if `limitator.reviewer.review.batch.max = 100` and `limitator.review.query.batch.limit=50`, one recheck task will verify 100 unique keys, and each query from the source or target end will query 50 unique keys. Therefore, the recheck task will query the database twice. |  oboms-verifier-2.0.0-xxx  and later |
| filter.verify.rectify.type | no | The data rectification setting parameter. Valid values: `no` and `now`. <ul><li>`no`: Indicates that inconsistent data is not rectified. </li><li>`now`: Indicates that inconsistent data is immediately rectified. </li></ul><main id="notice" type='notice'><h4>Notice</h4><ul><li>Do not set this parameter to <code>now</code> in non-emergency scenarios. If you need to set this parameter, contact the OMS Community Edition technical support. </li><li>MySQL->OB_MySQL and OB_MySQL->OB_MySQL support automatic rectification in `oboms-verifier-2.0.0-xxx` and later versions, but not in `oboms-verifier-1.xxx` versions. </li></main>| All versions |
| filter.verify.inmod.tables |  None  | The configuration parameter for tables verified by using the inmode mechanism. OMS Community Edition supports general verification and inmode verification. The main difference is the data retrieval method on the target end. In inmode verification, the target end does not query data based on the split range. Instead, it retrieves all data from the source end through a split and calculates the primary key values. Then, it queries the target end based on the primary key values. </li></ul><main id="notice" type='notice'><h4>Notice</h4><p>In inmode verification, you cannot verify scenarios where the target end has data that the source end does not have. In addition, the verification performance will be degraded. </p></main>Here are some common scenarios: <ul><li>Configure all tables in the current task to use inmode verification: `filter.verify.inmod.tables=.*;.*;.*`</li><li>Configure the T1 table in the D1 database to use inmode verification: `filter.verify.inmod.tables = D1;T1;.*`</li><li>Configure the T1 and T2 tables in the D1 database to use inmode verification: `filter.verify.inmod.tables = D1;T1;.*\|D1;T2;.*`</li><li>Configure the T1, T2 tables in the D1 database and the T3, T4 tables in the D2 database to use inmode verification: `filter.verify.inmod.tables = D1;T1;.*\|D1;T2;.*\|D2;T3;.*\|D2;T4;.*`|  All versions |
| limitator.table.diff.max | 10000 | The maximum number of inconsistencies allowed for each table. If the number of inconsistencies in a table exceeds this value, the status of the table will be set to abnormal, and the data of the table will not be verified further.<main id="notice" type='notice'><h4>Notice</h4><p>Do not set this value to more than 10 million. </p></main>| All versions |
| limitator.ready.verify.record.queue.size | 64 | The number of data records waiting to be verified. |  oboms-verifier-2.0.0-xxx  and later |
| limitator.ready.rectify.record.queue.size | 64  | The number of data records waiting to be rectified. |  oboms-verifier-2.0.0-xxx  and later |
| limitator.sink.slice.queue.size | 64 | The size of the target split queue. |  oboms-verifier-2.0.0-xxx  and later |
| task.coordinatorSection.reviewTaskQueueSize | 64 | The size of the recheck task queue. |  oboms-verifier-2.0.0-xxx  and later |
| limitator.verify.thread.size |  8 | The number of verification threads. | oboms-verifier-2.0.0-xxx  and later |
| limitator.review.thread.size | 16 | The number of recheck threads. | oboms-verifier-2.0.0-xxx  and later |
| limitator.rectify.thread.size | 32 | The number of rectification threads. |  oboms-verifier-2.0.0-xxx  and later |
| limitator.slice.split.batch.size |  None | The number of unique keys concatenated in one query if the target end uses an in query. | oboms-verifier-1.0.23-20230904200300  and later |
| task.sourceMasterSection.matchAllColumn | true | Whether to verify all fields. Valid values: `true` and `false`. <ul><li>`true`: Indicates that all fields must be verified. </li><li>`false`: Indicates that not all fields in the source table need to be mapped to the target table. Only the mapped fields are verified, and the unmapped fields are not verified. </li></ul>  |  OMS Community Edition V4.2.4-CE and later |
| task.sourceMasterSection.excludeColumn |  None | The fields to be excluded from verification in the source table. Note that you cannot exclude fields in the primary key (PK) or unique key (UK). Otherwise, verification errors will occur. The format is `{"regular expression":"c1,c2,.."}`, where the regular expression matches the table name in the `schema.tablename` format.  | OMS Community Edition V4.2.4-CE and later |
| task.sourceMasterSection.joinField |  None  | The fields used for table join. The format is `{"database name.table name": "source field name:target field name,...."}`. Multiple fields are separated by commas (,).<br>If the source field name and target field name are the same, you can configure it as `{"database name.table name": "source field name,....."}`. | OMS Community Edition V4.2.11-CE and later |

The supported version in the preceding table refers to the version of the data verification component. You can view the current verification version of OMS Community Edition by following the steps below.

1. Log in to the server where OMS Community Edition is deployed.

2. Enter the Docker container.

   ```shell
   docker exec -it ${CONTAINER_NAME} bash
   ```

   <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p><code>CONTAINER_NAME</code> is the name of the container. </p>
   </main>

3. Run the following command to query the version of the verification component.

    ```shell
    rpm -qa | grep "verifier"
    ```
