# OceanBase 社区版至 Kafka 数据同步的性能排查和调优

## 性能排查步骤

1. 通过下述方法，判断 Store 组件是否存在瓶颈。

    1. 执行下述命令，从 CDC 日志中查询 CDC 处理记录的速度，单位为记录数/秒。

        ```SQL
        grep NEXT_RECORD_RPS libobcdc.log
        ```

        如果 CDC 的处理速度慢于源端的业务数据速度，可以通过下面的查询进一步判断是否是 OMS 社区版机器导致的问题。

    2. 确认 CDC 是否触发流量控制机制。

        ```SQL
        grep "NEED_SLOW_DOWN=1 PAUSED=1" libobcdc.log
        ```

        `NEED_SLOW_DOWN=1` 表示触发了流控，原因是内存占用比较高，会限制拉日志效率。CDC 由于 IO、机器 load 等问题导致触发流量控制机制，暂停读取数据操作以避免进一步加剧系统压力。

        `memory_limit` 参数用于调整限流阈值，您可以在 `/home/ds/store/store{port}/etc/libobcdc.conf` 中查看当前值，并可以根据需要调大参数的值。示例如下：

        ```shell
        liboblog.memory_limit=20G
        liboblog.part_trans_task_active_count_upper_bound=500000
        ```

    3. 如果没有触发流控，则查询拉取 CLOG 的日志，确认 RPC 耗时。

        ```SQL
        grep do_stat libobcdc.log
        [2025-04-21 16:05:13.905681] INFO  [TLOG.FETCHER] do_stat (ob_log_ls_fetch_stream.cpp:309) [20155][][T0][Y0-0000000000000000-0-0] [lt=9] [STAT] [FETCH_STREAM] stream="xxx.xxx.xxx.1:2882"(0x7fa62d4131f0:HOT)({tenant_id:1028, ls_id:{id:1002}})(FETCHED_LOG:153.11GB) traffic=41.85MB/sec log_size=438879806 size/rpc=13.50MB log_cnt/rpc=946 rpc_cnt=31(3/sec) single_rp
        c=0(0/sec)(upper_limit=0(0/sec),max_log=0(0/sec),no_log=0(0/sec),max_result=0(0/sec)) rpc_time=312357 svr_time=(queue=41,process=224677) net_time=(l2s=1146,s2l=83859) cb_time=2632 h andle_rpc_time=13739 flush_time=860 read_log_time=12870(log_entry=2600,trans=0) trans_count=0 trans_size=0.00B
        ```

        上述日志中显示 `rpc_time=312357 svr_time=(queue=41,process=224677)`，表示 RPC 耗时 312 毫秒，其中 Server 处理该 RPC 耗时 224 毫秒。通常 RPC 耗时仅在几十毫秒左右，由此可见 PRC 耗时过长。此时，您需要查询 OBServer 日志并调整相关参数。

        OBServer 日志中有关键字 `fetch_log done`，该行日志预期会打印拉取日志的统计信息。如果该行日志中的 `fetch_archive_time` 不为 0，说明从归档拉取的日志，则需要调大 `log_disk_size` 的值来加大 CLOG 的存储空间。

        ![omsce7](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oms/oms-ce/omsce7.png)

2. 排除 Store 组件的问题后，继续查看 Full-Import/Incr-Sync 组件性能相关参数配置。

## Full-Import/Incr-Sync 组件性能相关配置

通常调整 Source 中的 useSchemaCache 为 true，即可满足大多数场景的需要。如果仍未满足 RPS，您可以设置 buildRecordConcurrent 为 true。

### Source

| 参数  |    描述  |
|-------------|----------------|
| useSchemaCache |可选值包括 true 和 false，默认值为 false。<br>如果设置为 `true`，则 Store 组件读取数据时会缓存 Schema，加速 Store 消息转换。|
| buildRecordConcurrent | 读取 Store 消息异步转换，可选值包括 true 和 false。<br>如果设置为 true，表示从 Store 拉取数据进行消息转换时将采用并行的方式，并行的线程数和 workerNum 相同。|

### Sink

下面两个参数是设置 Kafka 生产者客户端属性。

| OMS 社区版配置 | 对应 Kafka 客户端的属性配置  |  描述 |
|-------------|------------------------|---------------|
| lingerMs  |  ProducerConfig.LINGER_MS_CONFIG | Kafka 发送批次数据等待时间。如果需要提高吞吐量，该参数可以增加每个批次发送的数据量。默认值为 10，单位为毫秒。|
| batchSize | ProducerConfig.BATCH_SIZE_CONFIG | Kafka 每个批次发送数量的最大值，Kafka 客户端攒批发送。默认值为 1048576，单位为字节（1 MB）。|
| workerNum |     | Sink 并发工作线程，默认值为 16。|

coordinator 中的 enablePreprocessConfig 为 true 时，会自动根据 JVM 内存自动设置 lingerMs 和 batchSize。如果您手动配置了这两个参数，则以您手动配置的为准。

```shell
# 查看自动配置的参数
grep "auto set " connector.log
# 查看程序最终使用的配置
cat conf/runningConf.json
```

### coordinator

OMS 社区版 Shuffle 相关配置

|   参数       |    描述     |
|-----------------|--------------------|
| shuffleBucketSize   | 分桶数量。通常 OMS 社区版会读取分桶中的一批数据发送，并且在完成发送的情况下才会发送该分桶中的下一批数据，因此该配置的数量多少决定了可以同时发送的记录数，默认值为 128。|
| shuffleFlushIntervalMs | 定时读取分桶数据的时间间隔，间隔越小越实时。单位为毫秒，默认值为 100。 |
| shuffleMinBatchSize | 当分桶中记录数小于 shuffleMinBatchSize 值时，等待 shuffleFlushIntervalMs 后，再读取发送。默认值为 20。 |
| shuffleMaxBatchSize | 每次最大 shuffleMaxBatchSize 调记录发送，读取默认 64。|

## Arthas 性能分析

```SQL
# 登录 OMS 社区版容器
cp /root/arthas-bin.zip /home/ds
su - ds
unzip arthas-bin.zip

/opt/alibaba/java/bin/java -jar arthas-boot.jar pid(增量组件进程号)
profiler start
profiler getSamples
profiler status
# 等待 1 分钟后执行停止命令，会输出火焰图到 html 文件
profiler stop --format html
# 退出 Arthas
exit
```
